# 实时流数据管道设计

**状态**: 🚧 设计中（早期讨论）

**创建日期**: 2026-03-06

---

## 背景

因子引擎需要实时行情数据流支持。当前数据源为 miniqmt (XtQuant) 订阅，需要设计可靠的流处理管道。

---

## 当前理解的需求

```
[miniqmt 订阅] ──▶ [???] ──▶ [因子引擎] ──▶ [QuestDB]
                     │
              需要解决:
              - 解耦
              - 断点续传
              - 可靠消费
```

---

## 已讨论的设计决策

### 1. 灾备恢复策略（ADR-023 补充）

| 决策项 | 决策 | 理由 |
|--------|------|------|
| 分钟级数据灾备 | **上游可重发** | 把复杂度推给数据源，本地存储保持简单 |
| Parquet 冷备 | **不记录实时流分钟数据** | 避免存储翻倍，实时数据有时效性 |

### 2. 消息队列选型

| 选项 | 结论 |
|------|------|
| Redis Streams (Kvrocks) | ✅ 选择 |
| RabbitMQ | ❌ 不需要 |
| Kafka | ❌ 过重 |

**理由**：
- Kvrocks 已部署，复用现有组件
- Kvrocks 完全兼容 Redis Streams（Consumer Group 支持）
- 容量可控（当日盘中数据约 240 MB）

### 3. 消费语义

| 决策项 | 决策 |
|--------|------|
| 语义 | At-Least-Once |
| ACK 时机 | QuestDB 写入成功后 |
| 处理模式 | **批量 ACK** |
| 幂等性 | QuestDB 主键/时间戳去重 |

### 4. miniqmt 回放能力

| 能力 | 支持 | 说明 |
|------|------|------|
| 历史数据拉取 | ✅ | `download_history_data()` |
| 实时订阅 | ✅ | `subscribe_quote()` |
| 断点续传 | ⚠️ 需要设计配合 | 从历史 API 补齐 |

## 业界最佳实践：行情数据可靠性保障

> 调研来源：FIX 协议、金融行情 API 架构设计、高频交易系统

### 核心机制：序列号 + 心跳 + 推拉结合

```
┌─────────────────────────────────────────────────────────────────────┐
│                     业界标准：三重保障                               │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  1. 序列号 (Sequence Number)                                        │
│     ┌─────────────────────────────────────────────────────────┐    │
│     │  每条消息携带单调递增的 seq                               │    │
│     │  客户端检测 seq 跳跃 → 发现丢包 → 触发回补                │    │
│     │  例: 收到 100, 102 (跳过 101) → 检测到缺失               │    │
│     └─────────────────────────────────────────────────────────┘    │
│                                                                     │
│  2. 心跳 (Heartbeat)                                                │
│     ┌─────────────────────────────────────────────────────────┐    │
│     │  定期发送心跳消息 (如 30s)                                │    │
│     │  检测连接状态 + 序列号间隙                                │    │
│     │  心跳超时 → 连接异常 → 重连 + 全量同步                    │    │
│     └─────────────────────────────────────────────────────────┘    │
│                                                                     │
│  3. 推拉结合 (Push + Pull Hybrid)                                   │
│     ┌─────────────────────────────────────────────────────────┐    │
│     │  实时: WebSocket/Push (低延迟)                           │    │
│     │  补齐: REST API/Pull (按需回补)                          │    │
│     │  检测到缺失 → 自动调用 REST API 回补                     │    │
│     └─────────────────────────────────────────────────────────┘    │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### FIX 协议标准做法

FIX 协议是金融行业机构间通信的事实标准：

| 机制 | FIX 实现 | 说明 |
|------|----------|------|
| **序列号** | `MsgSeqNum` 字段 | 每条消息单调递增 |
| **间隙检测** | 客户端维护 `expected_seq` | 收到不连续 → 发送 Resend Request |
| **心跳** | `Heartbeat` 消息 | `HeartBtInt` 定义间隔 (如 30s) |
| **重传请求** | `ResendRequest (35=2)` | `BeginSeqNo` + `EndSeqNo` |
| **重复标记** | `PossDupFlag (43=Y)` | 重传消息标记为可能的重复 |

```
间隙检测与恢复流程:

CLIENT                              BROKER
   │                                   │
   │ ◀─── Message(seq=100) ──────────  │
   │                                   │
   │ ◀─── Message(seq=102) ──────────  │  ← 检测到跳跃，缺失 101
   │                                   │
   │ ──── ResendRequest(101-101) ────▶ │
   │                                   │
   │ ◀─── Message(seq=101, PossDup=Y) ─│  ← 重传
   │                                   │
   │ (继续处理，seq=101 → 102)         │
```

### WebSocket "静默丢包" 问题

> 高频行情场景下的常见问题

```
问题场景:
- 市场剧烈波动 → 突发流量 (Burst Traffic)
- 服务端缓冲区溢出 → 静默丢弃数据帧
- 客户端连接显示正常，实则已漏掉关键数据

解决方案:
1. 消息携带 seq 字段 (单调递增)
2. 客户端检测 seq 跳跃
3. 自动触发 REST API 数据回补
```

### 推荐架构：REST (快照) + WebSocket (流式)

```
┌──────────────────────────────────────────────────────────────────────┐
│                        推拉结合架构                                   │
│                                                                      │
│  [数据源]                                                            │
│     │                                                                │
│     ├──── WebSocket (Push) ────▶ 实时流 ──▶ [Stream/Kafka]          │
│     │        │                   (低延迟, 带 seq)                    │
│     │        │                                                        │
│     │        └── 检测到 seq 跳跃 ──┐                                  │
│     │                              │                                  │
│     │                              ▼                                  │
│     └──── REST API (Pull) ◀───── 回补缺失数据                        │
│              (按需, 历史数据)                                         │
│                                                                      │
│  [消费端]                                                            │
│     │                                                                │
│     ├──── 正常消费: 按序处理                                          │
│     │                                                                │
│     └──── 检测缺失: 标记 + 延迟处理 (等回补) 或 跳过                  │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

### 针对 miniqmt 的适配方案

由于 miniqmt 是第三方 SDK，可能不提供原生序列号机制：

```
自建序列号层:

[miniqmt 订阅]
     │
     ▼
[Producer 封装层]  ←── 在这里添加 seq
     │
     ├─ 为每条消息分配 seq (全局或按标的)
     │
     ├─ 定期发送心跳 (包含最新 seq)
     │
     └─ XADD to Stream (带 seq 字段)
```

## 5. 生产者端可靠性保障（待决策）

> ⚠️ **核心问题**：如何保证 miniqmt 不漏发？如何检测和补偿？

### 问题分析

```
[miniqmt 订阅] ──XADD──▶ [Stream]
      │
      └─ 可能的漏发场景:
         1. 网络中断
         2. miniqmt 进程崩溃
         3. 某些标的订阅失败
         4. 盘中临时断线
```

### 可选方案

#### 方案 A：时间窗口检测 + 补偿

```
原理：定期检查每个标的是否收到预期时间点的数据

┌─────────────────────────────────────────────────────────┐
│  检测器 (每 N 分钟运行一次)                              │
│                                                         │
│  1. 获取订阅标的列表                                     │
│  2. 检查每个标的最后收到的时间戳                          │
│  3. 如果 gap > 阈值 (如 5 分钟):                        │
│     → 标记为缺失                                        │
│     → 触发补偿: download_history_data() 补齐            │
│     → 写入 Stream                                       │
└─────────────────────────────────────────────────────────┘
```

| 优点 | 缺点 |
|------|------|
| 实现简单 | 有延迟（依赖检测周期） |
| 不依赖上游改造 | 可能漏检短时中断 |
| 可复用 miniqmt 历史接口 | 检测周期短则开销大 |

#### 方案 B：序列号/心跳检测

```
原理：miniqmt 端主动上报心跳和序列号

[miniqmt Producer]
    │
    ├─ 每分钟数据: XADD stream:* data ...
    │
    └─ 心跳: XADD heartbeat:* ts=... count=... codes=...

[Detector]
    │
    └─ 检查心跳是否正常，count 是否匹配
```

| 优点 | 缺点 |
|------|------|
| 实时检测 | 需要改造 Producer |
| 精确知道缺失范围 | 增加复杂度 |
| 可区分"无数据"vs"漏发" | miniqmt 可能不支持 |

#### 方案 C：双轨校验（推荐待评估）

```
原理：实时流 + 批量校验双轨并行

[实时轨道]  miniqmt 订阅 → Stream → QuestDB
                │
                ▼
[校验轨道]  定时任务 → miniqmt 历史数据 → 对比 QuestDB → 发现差异 → 补偿
```

```
校验逻辑:
1. 每隔 N 分钟，获取最近 N 分钟的预期数据（从 miniqmt 历史接口）
2. 对比 QuestDB 中的实际数据
3. 发现缺失 → 补齐
4. 记录校验结果日志
```

| 优点 | 缺点 |
|------|------|
| 双重保障 | 实现复杂度较高 |
| 可发现任何原因的缺失 | 校验有额外开销 |
| 不依赖实时轨道改造 | 需要定时调度 |

### 检测维度

| 维度 | 检测方法 | 阈值建议 |
|------|----------|----------|
| **时间连续性** | 检查分钟数据时间戳是否连续 | gap > 3 分钟告警 |
| **标的完整性** | 检查订阅列表中每个标的都有数据 | 缺失 > 10 个告警 |
| **数据量异常** | 检查每分钟收到的数据量是否在正常范围 | 偏离均值 50% 告警 |
| **心跳超时** | Producer 心跳超时 | > 30 秒无心跳告警 |

### 补偿流程（草案）

```
检测到缺失
    │
    ▼
记录日志 (标的代码, 缺失时间段, 原因)
    │
    ▼
调用 miniqmt.download_history_data(code, start=缺失开始, end=缺失结束)
    │
    ▼
写入 Stream (标记为补偿数据)
    │
    ▼
正常消费流程
```

### 待决策项

| 问题 | 选项 | 建议 |
|------|------|------|
| 检测方案 | A: 时间窗口 / B: 心跳+seq / C: 双轨校验 | **业界倾向 B 或 C** |
| 序列号实现 | miniqmt 原生 / 自建 | **需调研 miniqmt 能力** |
| 检测周期 | 1min / 5min / 10min | 取决于容忍延迟 |
| 补偿数据标记 | 是否需要区分实时/补偿 | 建议标记，便于审计 |
| 校验持久化 | 校验结果是否存储 | 建议存储，便于排查 |

### 推荐方案（待确认）

基于业界最佳实践，推荐 **方案 B+C 混合**：

```
┌─────────────────────────────────────────────────────────────────────┐
│                    推荐方案：心跳检测 + 定时校验                       │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  实时检测层 (Heartbeat + 时间戳)                                     │
│  ─────────────────────────────────                                  │
│  • Producer 每 30s 发送心跳 (包含订阅标的列表 + 最新时间戳)           │
│  • Detector 检查心跳是否超时 (>60s 无心跳 = 告警)                    │
│  • 检查每个标的时间戳是否滞后 (gap > 3min = 触发补偿)                │
│                                                                     │
│  定时校验层 (每日/每小时)                                            │
│  ─────────────────────────────────                                  │
│  • 定时任务对比 QuestDB 数据量与预期                                 │
│  • 发现差异 → 从 miniqmt 补齐                                        │
│  • 记录校验报告                                                      │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**优点**：
- 实时检测发现问题，快速补偿
- 定时校验兜底，防止漏检
- 不强依赖 miniqmt 提供序列号

## 待深入讨论的问题

### 高优先级

1. **生产者端可靠性** ⬆️ 新增
   - 检测方案选择
   - 补偿流程设计

2. **流分片策略**
   - 单 Stream vs 多 Stream（按标的/类型分片）
   - 分片对 Consumer Group 的影响

2. **消息格式**
   - JSON vs 二进制 vs 扁平 field-value
   - 压缩与否

3. **断点续传完整流程**

   - 从 miniqmt 补齐的具体逻辑

4. **消费失败处理**
   - 重试策略（次数、间隔）
   - 死信队列设计
   - 人工介入机制

5. **多 Consumer 扩展**

   - 负载均衡策略

6. **监控与告警**
   - Pending List 堆积阈值
