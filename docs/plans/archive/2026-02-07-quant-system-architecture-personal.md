# Ditto 个人量化架构设计（精简版）

> 日期：2026-02-07
> 状态：建议稿（面向个人量化、可直接落地）
> 目标：减少过度分层，优先可用性、可维护性、可复现性

---

## 1. 结论先行

针对你当前问题，结论如下：

1. **不需要单独拆出 application 模块（package）**。
   对个人量化而言，`apps/port` 作为组合根与流程编排入口已经足够。

2. **DataHub 仍建议保留独立模块**，不要并入纯 infra。
   因为 DataHub 承担的是数据语义能力（PIT、时态、版本、数据契约），不是通用基础设施。

3. **数据分层可精简为 2 层主干 + 1 个可选层**：
   - `D1 事实数据层`（清洗后的统一事实数据）
   - `D2 衍生数据层`（因子/特征/标签）
   - `D0 原始快照层`（可选，按需启用）

---

## 2. 业界最佳实践对你场景的启发

### 2.1 对个人量化真正有价值的共识

从主流框架可提炼出一致结论：

1. 先保证“研究和回测用的是同一份标准化数据语义”。
2. 数据要可复现（版本/快照），但不必一开始就搭大而全数据湖。
3. 流程编排可以很薄，核心是边界清晰而非模块数量多。

### 2.2 与你问题直接相关的实践映射

1. LEAN：强调事件驱动与可插拔组件，但并不要求你单独拆一个“application 包”。
2. Backtrader：`Cerebro` 集中编排，数据与策略直接接入，结构非常务实。
3. Zipline：核心是“标准化 bundle + 版本化 ingest”，重点在可复现，不在层次名词。
4. Qlib：重视 `DataHandler + Dataset` 的数据处理与训练接口，但并不强推复杂分层命名。
5. Freqtrade（零售/个人常见）：以 OHLCV + 指标/特征为主，数据层可非常精简。

## 3. 推荐的目标架构（个人量化版）

## 3.1 包级划分（保持简单）

```
apps/
  port/                    # 组合根 + API/CLI/Jobs 编排（唯一入口）

packages/
  foundation/              # 通用基础能力（日志、指标、并发、配置）
  datahub/                 # 数据语义与数据服务（独立保留）
  core/                    # 因子/回测/风险/策略逻辑
```

> 不新增 `packages/application`。
> `application` 的职责由 `apps/port/services` 承担即可。

## 3.2 责任边界（强约束）

1. `foundation`：通用技术能力，不含业务数据语义。
2. `datahub`：数据契约、PIT、版本、读写服务、存储适配。
3. `core`：策略研究、回测、风控规则。
4. `apps/port`：调度、重试、告警、跨域编排。

## 4. 数据分层（2 层主干）

## 4.1 分层定义

### `D1 事实数据层`（必需）

职责：

1. 存放清洗后、标准化后的可直接查询事实数据。
2. 统一主键与时间语义（`sid`, `trade_date`, `effective_*`, `knowledge_date`）。
3. 承载回测、研究、报表的共同输入。

示例数据集：

1. `market.stock.bars.daily`
2. `market.etf.bars.daily`
3. `metadata.instrument`
4. `metadata.calendar`
5. `market.stock.adj_factor`

### `D2 衍生数据层`（必需）

职责：

1. 基于 D1 计算的因子、特征、标签、训练样本。
2. 保存计算版本与依赖信息，保证可重现。

示例数据集：

1. `factor.value.pb`
2. `factor.momentum.20d`
3. `feature.technical.rsi_14`
4. `label.forward_return.5d`

### `D0 原始快照层`（可选）

默认关闭，按需开启。

建议只在以下场景开启：

1. 数据源经常改历史值。
2. 你频繁遇到“同日重跑结果不一致”。
3. 你开始做多源对账与审计。

---

## 5. 为什么 2 层足够（个人量化）

对个人量化，最关键不是层数，而是这三件事：

1. **统一事实口径**：D1 是唯一事实来源。
2. **衍生可重现**：D2 每次产物可追溯输入与版本。
3. **PIT 安全**：查询显式 `asof`，避免未来函数。

只要这三件到位，D0 是否完整保留并不影响你的首期收益与研发效率。

---

## 6. DataHub 在精简架构中的定位

## 6.1 保留独立模块的理由

如果把 DataHub 并入 infra，会出现两个问题：

1. PIT/版本/时态语义会被“工具化”，边界变模糊。
2. Core 与 Port 容易绕过统一数据契约，形成隐式耦合。

因此：**DataHub 独立，但保持小而硬的边界**。

## 6.2 DataHub 内部也要精简

建议只保留三类组件：

1. `QueryService`：查询与 PIT 过滤（只读）。
2. `WriteService`：写入、幂等、去重策略（只写）。
3. `Store`：纯存储访问（无业务编排）。

## 8. 迁移策略（从当前到精简版）

### 步骤 1：冻结边界（1-2 周）

1. 定义 D1 数据集清单（先 10 个核心集）。
2. 定义 D2 数据集清单（先 5 个核心因子/特征）。
3. 冻结 Query/Write 接口签名。

### 步骤 2：收敛 DataHub（2-4 周）

1. 重服务拆分为 Query/Write。
2. 去掉多余兼容层与重复 API。
3. 建立最小版本登记（`batch_id/version_id/checksum`）。

### 步骤 3：回测闭环（2-4 周）

1. 回测只读取 D1 + D2。
2. 报告记录输入版本，确保可重现。
3. 仅在“结果不可解释”时再引入 D0。

---

## 9. 反模式（你现在要避免）

1. 为了“看起来企业级”而增加模块。
2. 在 core 或 app 中绕过 DataHub 直接拼数据。
3. 过早建设完整原始层归档系统。
4. 文档与 API 命名长期不一致。

---

## 10. 最小可行验收标准

满足以下条件，即可认为架构成功：

1. 任意策略回测结果可追溯到 D1/D2 的版本号。
2. 所有行情与因子查询支持 `asof`。
3. 摄取任务失败后可重跑且结果一致。
4. `apps/port` 不新增独立 application package 仍可清晰编排。

---

## 11. 最终建议

你的直觉是对的：

1. 对个人量化，**不需要单独 application 模块**。
2. 数据层先做 **“清晰事实层 + 衍生层”** 就够了。
3. DataHub 应独立保留，但要做“小而硬”的数据语义边界，而不是大而全平台。

这条路径最符合个人量化的投入产出比，也最容易长期稳定演进。
