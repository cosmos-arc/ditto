# Ditto 量化系统架构设计（V2）

> 日期：2026-02-07
> 状态：提案（可直接作为下一阶段实施蓝图）
> 适用范围：Ditto 全系统（`apps/port` + `packages/core` + `packages/datahub` + `packages/foundation`）
> 命名约束：本文不使用 `silver/gold` 命名体系

---

## 1. 目标与边界

### 1.1 目标

构建一套可长期演进的量化系统，满足以下核心能力：

1. 数据可追溯、可重放、PIT 安全。
2. 研究回测与生产执行共享同一数据语义和关键算子。
3. 分层清晰，边界稳定，避免“反复重构但不收敛”。
4. 支持从日频到分钟级的稳步扩展（先稳后快）。

### 1.2 非目标（当前阶段）

1. 不追求首期 Tick/L2 高频撮合级模拟。
2. 不追求首期分布式大集群（先模块化单体）。
3. 不追求一次性覆盖全资产全市场全策略形态。

## 2. 顶层架构

### 2.1 分层视图

```
┌──────────────────────────────────────────────────────────────┐
│                       应用层 (apps/port)                     │
│  API/CLI/Job 编排、配置装配、依赖注入、任务调度、告警出口    │
└──────────────────────────────────────────────────────────────┘
                           ↓
┌──────────────────────────────────────────────────────────────┐
│                      领域层 (packages/core)                  │
│  因子引擎、质量引擎、回测引擎、组合与风险规则                 │
└──────────────────────────────────────────────────────────────┘
                           ↓
┌──────────────────────────────────────────────────────────────┐
│                    数据平台 (packages/datahub)               │
│  数据接入、标准化、主题存储、衍生产物、PIT/版本能力            │
└──────────────────────────────────────────────────────────────┘
                           ↓
┌──────────────────────────────────────────────────────────────┐
│                 基础设施层 (packages/foundation)             │
│  配置、日志、指标、追踪、并发控制、缓存、通用组件             │
└──────────────────────────────────────────────────────────────┘
```

### 2.2 依赖规则

1. `core -> datahub -> foundation` 单向依赖。
2. `apps/port` 作为唯一组合根（Composition Root）。
3. 跨域编排只允许在 `apps/port`，域服务之间禁止直接互调。

### 2.3 DataHub 模块定位决策

围绕“`datahub` 是独立模块还是归入 `infra`”的决策，给出三个备选：

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| A | `datahub` 完全归入 `foundation/infra` | 包数量更少 | 数据语义被基础设施稀释，领域边界变弱 |
| B | `datahub` 作为独立数据平台模块（推荐） | 数据契约、PIT、版本能力可独立演进 | 需要更严格边界治理 |
| C | `datahub` 大幅拆散到 `apps/application` | 贴近业务编排 | 易形成重复实现与跨服务漂移 |

最终结论：采用 **方案 B**。

1. `datahub` 不应被定义为纯 infra，它承载了高密度数据语义（PIT、时态、主键、版本）。
2. `datahub` 也不应被拆碎到 application；application 只做流程编排，不拥有底层数据语义。
3. `foundation` 只保留通用基础能力，不承载业务数据语义。

### 2.4 模块职责归属（强约束）

| 能力 | foundation | datahub | core | apps/port |
|---|---|---|---|---|
| 日志/指标/追踪/锁/缓存 | ✅ | ❌ | ❌ | ❌ |
| 数据模型时态语义（asof/effective/knowledge） | ❌ | ✅ | ❌ | ❌ |
| 数据接入适配、标准化、版本化、存储 | ❌ | ✅ | ❌ | ❌ |
| 因子质量评估、回测规则、风险规则 | ❌ | ❌ | ✅ | ❌ |
| 任务调度、重试、通知、跨域流程编排 | ❌ | ❌ | ❌ | ✅ |

> 判定规则：只要某能力包含“业务数据语义”，优先归 `datahub` 或 `core`，不要下沉到 `foundation`。

## 3. 数据平台架构（DataHub V2）

### 3.1 数据分层命名（替代银金铜）

采用 `L0~L3` 语义层，不绑定任何特定平台术语：

1. `L0 原始快照层`：外部源原始响应快照，Append-Only。
2. `L1 标准化层`：统一字段、类型、主键、时态语义。
3. `L2 主题实体层`：按业务主题组织的可查询实体。
4. `L3 衍生产物层`：因子、特征、标签、训练样本。

### 3.2 各层职责

| 层级 | 核心职责 | 存储建议 | 更新策略 |
|---|---|---|---|
| `L0 原始快照层` | 数据追溯、审计、重放输入 | Parquet/压缩 JSON | 只追加 |
| `L1 标准化层` | 统一 schema、主键、时态列 | Parquet + SQLite 元数据 | 重算/增量 |
| `L2 主题实体层` | 可直接服务研究与业务查询 | Parquet/SQLite 混合 | Upsert + 版本 |
| `L3 衍生产物层` | 因子特征标签及训练集 | Parquet + 元数据注册 | 全量/增量均可 |

### 3.3 核心数据不变量

所有时序数据默认遵循以下约束：

1. 主标识：`sid`（内部唯一标识），禁止业务逻辑依赖外部代码。
2. 时间语义：
   - 事件时间：`trade_date` 或 `event_time`
   - 生效区间：`effective_from`, `effective_to`
   - 认知时间：`knowledge_date`
3. 每次写入必须可追溯：`batch_id`, `version_id`, `checksum`。
4. 所有对外查询必须明确 PIT 语义（提供或推导 `asof`）。

## 4. 业务域与服务边界

### 4.1 域划分（DataHub）

1. `metadata`：标的、交易日历、行业、标识映射、标的池。
2. `market`：行情、状态、复权因子、指数成分等。
3. `fundamental`：财报、分红、预告快报等。
4. `capital`：融资融券、质押、估值、期货等。
5. `macro`：宏观指标及元数据。
6. `features`：技术特征与模型特征。
7. `factors`：风格/主题因子及元数据。

### 4.2 服务拆分原则

建议采用读写分离（CQRS）而非“超大统一服务”：

1. `XxxQueryService`：只读查询、拼接增强、PIT 过滤。
2. `XxxWriteService`：写入、幂等、并发锁、重复策略。
3. `Store`：纯存储访问，不承担业务编排。

> 这能避免 `MarketService` 一类服务同时承担读写增强锁控制，导致体积失控和重构震荡。

## 5. 数据摄取与质量控制

### 5.1 摄取流水线

```
Extract -> L0 快照 -> Schema/主键校验 -> 标准化转换 -> DQ 规则校验 -> L1/L2 写入 -> 元数据登记
```

### 5.2 质量控制分层

1. `Schema 规则`：列存在、类型、主键唯一。
2. `技术规则`：空值率、重复率、范围与异常值。
3. `业务规则`：例如 OHLC 关系、交易日一致性、状态约束。
4. `对账规则`：多源差异比较（可配置优先级/投票策略）。

### 5.3 阻断策略

1. `ERROR`：阻断写入。
2. `WARNING`：放行但记录告警与审计。
3. `ALERT`：放行并触发高优先级通知。

## 6. PIT 与版本设计

### 6.1 查询规范

所有对外查询接口支持：

1. `asof`：查询时点（必须有默认策略）。
2. `source`：数据源维度（可选）。
3. `version`：快照版本（可选，默认 latest）。

### 6.2 版本模型

1. `batch_id`：一次摄取任务的唯一编号。
2. `version_id`：数据集可读版本号（逻辑快照）。
3. `checksum`：数据完整性指纹。
4. `freeze`：可复现快照（用于回测和模型训练重现）。

---

## 7. 因子与特征系统

### 7.1 概念边界

1. `Feature`：模型输入，偏描述与预测。
2. `Factor`：投资信号，偏解释与组合构建。

### 7.2 统一表达式层

建议维护统一算子层，避免研究与生产两套逻辑：

1. 时序算子：`ts_mean`, `ts_std`, `ts_rank`, `delta`。
2. 截面算子：`rank`, `zscore`, `neutralize`。
3. 组合算子：`clip`, `winsorize`, `orthogonalize`。

### 7.3 存储与注册

每个因子/特征最少记录：

1. `code`, `name`, `owner`, `definition`（表达式/代码版本）。
2. `input_datasets`, `dependencies`。
3. `run_id`, `version_id`, `created_at`。
4. `quality_metrics`（覆盖率、稳定性、IC/IR 等）。

---

## 8. 研究、回测与执行双路径

### 8.1 双路径原则

1. 研究路径：吞吐优先（向量化）。
2. 执行路径：真实性优先（事件驱动）。
3. 两条路径共享数据语义、PIT 规范和关键算子。

### 8.2 回测引擎最小闭环

首期最小可用闭环：

1. 信号生成（因子或模型输出）。
2. 选股与权重分配。
3. 成交模拟（含手续费、滑点、成交约束）。
4. 组合与风险统计。
5. 结果追溯到版本化数据快照。

## 11. 当前架构划分问题与修正

### 11.1 当前问题判定

当前 Ditto 架构的主要问题不是“层级数量太多”，而是“职责混放与边界漂移”：

1. `datahub` 内存在“查询服务 + 写入控制 + 兼容桥接”混合，导致局部服务过重。
2. `application` 与 `datahub` 之间部分编排边界尚不稳定，易出现重复逻辑。
3. `foundation` 与 `datahub` 的责任线偶有模糊（例如数据语义相关逻辑下沉风险）。
4. 文档与真实 API 漂移，放大了重构成本和认知负担。

### 11.2 修正原则

1. `foundation`：永远不承载数据业务语义。
2. `datahub`：承载数据语义与数据能力，但不承载跨域业务流程。
3. `apps/port`：承载跨域编排、任务调度、失败补偿、告警通知。
4. `core`：承载策略研究、回测与风险规则，依赖 datahub 获取语义一致的数据。

### 11.3 结构化修正动作

1. 将 `datahub` 服务按 CQRS 拆成 Query/Write，避免单服务膨胀。
2. 将跨域 ingest/backfill/repair 编排统一收敛到 `apps/port/services`。
3. 对 `datahub` 对外 API 做版本冻结并设立兼容退役窗口。
4. 用静态检查与测试约束依赖方向，防止边界回退。

## 12. 非功能性要求

### 11.1 性能

1. 日频批量任务：分钟级完成。
2. 分钟级增量：可按批次稳定处理，不丢不重。
3. 查询：常见窗口查询具备稳定低延迟。

### 11.2 可靠性

1. 写入幂等。
2. 失败可重试、可补偿。
3. 关键操作有审计日志。

### 11.3 可观测性

1. 指标：吞吐、延迟、失败率、DQ 命中率。
2. 日志：结构化字段（dataset、batch_id、version_id）。
3. 链路：关键任务 trace 可追踪。

## 13. 实施路线图（90 天）

### 阶段 A（第 1-3 周）：边界冻结

1. 冻结 DataHub 对外 API（查询/写入/PIT 约定）。
2. 统一元数据库路径和版本登记入口。
3. 修复组合根和依赖注入的一致性问题。

### 阶段 B（第 4-8 周）：数据主干稳定

1. 完成 `L1 标准化层` 与 `L2 主题实体层` 主流程。
2. 完成核心数据集（metadata + market 日频）PIT 查询能力。
3. 落地 DQ 规则与阻断策略。

### 阶段 C（第 9-12 周）：产出层与回测闭环

1. 建立 `L3 衍生产物层`（因子/特征/标签）。
2. 打通“数据版本 -> 因子计算 -> 回测复现”闭环。
3. 输出首版架构验收报告（质量、性能、稳定性）。

## 14. 模块拆分建议（可选增强）

在保持当前包结构的前提下，建议对 `datahub` 做“内部逻辑拆分”而不是“仓库级拆散”：

1. `datahub.kernel`：时态模型、版本模型、通用存储策略。
2. `datahub.domain`：metadata/market/fundamental 等域服务（Query/Write）。
3. `datahub.pipeline`：数据接入与标准化原语（被 application 编排调用）。
4. `apps/port.services`：摄取、回填、修复等业务流程编排。

这样可以同时满足：

1. 保持 `datahub` 的独立模块定位。
2. 防止 datahub 内部继续“无限增胖”。
3. 避免过早微服务化引入运维复杂度。

---

## 15. 反模式清单（必须避免）

1. 域服务跨域直接调用，导致隐式依赖网。
2. Store 承担业务编排逻辑，导致难测难拆。
3. 文档 API 与代码 API 长期漂移。
4. 把“向后兼容”当成永久层，不设退役时间。
5. 过早引入大而全中间件，忽视核心链路稳定。

---

## 16. 验收标准

满足以下条件可判定 V2 架构落地成功：

1. 关键数据集支持 PIT 查询且有集成测试覆盖。
2. 数据摄取失败可重放，可定位到 `batch_id`。
3. 因子/特征结果可追溯到输入版本与运行参数。
4. 研究回测与生产查询使用同一语义定义。
5. 架构边界可由静态规则和测试持续守护。

---

## 17. 总结

该方案的核心不是“再造一套新名词”，而是：

1. 用稳定边界替代反复重构。
2. 用可追溯数据契约支撑研究与生产一致性。
3. 用分阶段落地保证系统可持续演进。

如果按本文推进，Ditto 可以从“架构想法丰富”进入“架构持续收敛且可交付”的状态。
