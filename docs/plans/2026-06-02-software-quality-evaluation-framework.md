# 软件系统质量评价框架

> **版本**: v1.0
> **日期**: 2026-06-02
> **用途**: Ditto 项目自评参考，建立代码/架构/测试/流程/运维/领域六维评价标准

---

## 1. 概述

### 1.1 目的

为 Ditto 量化交易平台建立一套全面、可量化、有业界依据的系统质量评价框架，用于：

- 定期自评，量化当前质量水平
- 发现薄弱环节，指导改进优先级
- 为架构评审和代码审查提供标准参考

### 1.2 业界标准来源

本框架综合了以下业界最佳实践与标准：

| 标准 | 提供什么 | 版本/年份 |
|------|---------|----------|
| **ISO/IEC 25010:2023** (SQuaRE) | 质量特性分类体系（9 大特性） | 2023 |
| **ISO/IEC 5055:2021** (CISQ) | 可自动化的结构质量弱点计数（CWE 映射） | 2021 |
| **SIG/TÜViT 质量模型** | 8 大可度量属性 + 星级基准（4000 亿行代码数据） | 2024 |
| **SQALE** | 技术债量化模型（修复成本 / 债务比率 A-E 级） | — |
| **ATAM** (SEI/Carnegie Mellon) | 架构评估方法论（场景驱动、质量属性权衡） | — |
| **Fitness Functions** (ThoughtWorks) | 自动化架构守护（原子/整体/触发/持续/静态/动态） | 2017+ |
| **DORA** (Google) | 工程效能度量（4+1 指标，精英/高/中/低四档） | 2024 |
| **SPACE** (GitHub/Microsoft) | 开发者生产力五维框架 | 2021 |
| **Fowler 技术债四象限** | 技术债分类（审慎/鲁莽 × 有意/无意） | — |
| **Google/Microsoft 代码审查标准** | 审查最佳实践（PR 大小、审查响应、审查清单） | — |

### 1.3 六维评价框架

```
┌──────────────────────────────────────────────────────┐
│              软件系统质量评价框架                       │
├──────────────────────────────────────────────────────┤
│                                                      │
│  ① 代码质量 ──── 静态分析、类型安全、复杂度、重复度   │
│  ② 架构质量 ──── 分层、耦合、内聚、模块独立性         │
│  ③ 测试质量 ──── 覆盖率、分层、确定性、速度           │
│  ④ 工程流程 ──── CI/CD、代码审查、DORA、SPACE         │
│  ⑤ 运维质量 ──── 可观测性、可靠性、性能、安全         │
│  ⑥ 领域特有 ──── 回测确定性、数据完整性、风控独立性   │
│                                                      │
│  业界来源: ISO 25010 + SIG + SQALE + ATAM            │
│           + DORA + SPACE + Fitness Functions          │
└──────────────────────────────────────────────────────┘
```

### 1.4 评级体系

采用 SIG 星级基准（基于 4000 亿行代码的百分位排名）和 DORA 四档评级：

| 评级 | 含义 | SIG 百分位 | 适用场景 |
|------|------|-----------|---------|
| 🟢 **优秀** (4-5★ / Elite) | 业界前 25% | Top 5-25% | 活跃演进系统的目标 |
| 🟡 **合格** (3★ / High) | 业界平均水平 | Median | 维护模式系统的最低标准 |
| 🟠 **待改进** (2★ / Medium) | 低于平均 | Bottom 25-50% | 需要关注 |
| 🔴 **需改进** (1★ / Low) | 业界末位 | Bottom 5-25% | 必须立即整改 |

### 3.4 Fowler 技术债四象限

用于分类和决策技术债的优先级：

```
                    | Deliberate（有意）         | Inadvertent（无意）
--------------------|---------------------------|---------------------------
Prudent（审慎）      | "先上线，后重构"          | "现在理解了，但已太迟"
                    | （战略性捷径，有偿还计划）  | （学习型债务，不可避免）
--------------------|---------------------------|---------------------------
Reckless（鲁莽）     | "没时间做设计"            | "什么是好设计？"
                    | （有意识的疏忽）           | （无知型混乱）
```

**Ditto V2 架构整改**属于 **Prudent-Inadvertent**（审慎-无意）：通过迭代学习了更好的架构，现在正在偿还。这类债务是不可避免的，关键是有意识地持续偿还。

## 5. 维度④：工程流程

> **业界来源**: DORA 四+一指标 (2024)、SPACE 框架 (2021)、Google/Microsoft 代码审查标准

### 5.1 DORA 指标（2024 版，适配量化平台）

| # | 指标 | 含义 | 🟢 精英 | 🟡 高 | 🟠 中 | 🔴 低 |
|---|------|------|---------|-------|-------|-------|
| P1 | **部署频率** | 代码部署到生产的频率 | 按需（多次/天） | 周→月 | 月→半年 | > 半年 |
| P2 | **变更前置时间** | 从 commit 到可用的时间 | < 1 天 | 1天→1周 | 1周→1月 | 1-6月 |
| P3 | **变更失败率** | 导致故障的部署占比 | 0-15% | 16-30% | 31-45% | 46-60% |
| P4 | **恢复时间** | 故障后恢复服务的时间 | < 1 小时 | < 1 天 | 1天→1周 | 1-6周 |
| P5 | **返工率** (2024 新增) | 计划外修复部署占比 | < 15% | 15-25% | 25-35% | > 35% |

> **DORA 2024 关键变更**:
> - 恢复时间从"稳定性"重新分类为"吞吐量"维度
> - 新增返工率（Rework Rate）作为变更失败率的补充
> - 阈值是聚类分析结果，不是固定基准，应结合项目特点解读

| 性能基准 | 有 + 自动化回归检测 | 有基准 | 无基准 |
| 环境隔离 | 严格分离 + 验证 | 分离但无验证 | 混用 |

### 6.3 Fitness Functions 分类

参照 Neal Ford / ThoughtWorks 的演化架构 Fitness Functions 分类：

| 类型 | 定义 | Ditto 示例 |
|------|------|-----------|
| **Atomic（原子）** | 单一上下文，单一属性 | basedpyright 类型检查、import-linter 边界检查 |
| **Holistic（整体）** | 多上下文，多属性组合 | `pixi run -e dev check`（lint + type + test + arch） |
| **Triggered（触发式）** | 事件触发运行 | CI pipeline 每次提交触发 |
| **Continual（持续式）** | 持续验证 | 生产环境延迟监控 |
| **Static（静态）** | 固定阈值 | 测试覆盖率 ≥ 80% |
| **Dynamic（动态）** | 动态阈值 | 数据管道延迟根据数据量动态调整 |
