# Harness 与仓库组织重整：设计访谈记录

状态：十项决定及最终方案已确认；用户调用 to-spec 后，正式规格已发布为 [GitHub Issue #111](https://github.com/cosmos-arc/ditto/issues/111)，标记 ready-for-agent。本文件作为访谈来源保留，后续规格、验收和任务状态以该 Issue 为准；拆分后的任务与实施进度以该 Issue 的子任务为准。核查基线：`9e42fdd9`（PR #110 合并后的 main）。

## 目标

梳理从需求澄清、规划、实现、验证、评审到交付的开发流程，以当前 Matt skills 和实际宿主能力为基础；同时治理遗留文档、废弃目录、无用文件及其引用、发现入口和维护责任。此记录只承载本次设计与决策过程，不代替项目长期规范。

## 已确认决策

1. **工作流按风险分流。** 小改动直接实现与验证；需求不清或涉及架构的复杂任务展开必要的访谈、规格、拆票与审查。已确认决定跨阶段复用，不重复确认。
2. **本轮以治理与工程组织为主。** 覆盖开发 harness、skills、文档、脚本、工具与生成物组织；必要的源码引用调整纳入。独立业务架构和公共接口重构不自动扩入本次范围。
3. **普通历史主要通过 Git 追溯。** 已被替代且没有活跃引用的历史材料从当前目录树移除；有长期价值的 ADR、发布和审计证据选择性保留。实施前提供具体清单、引用检查和恢复方式。本项是保留原则，不是对未审查文件的删除授权。
4. **通用 skills 与项目治理分离。** Matt skills 保持上游独立维护，项目记录来源版本和安装/验证适配，不复制整套通用 skills 自行维护。长期决定见 [ADR 0012](../adr/0012-development-skills-ownership.md)。
5. **GitHub 管任务，仓库管长期知识。** GitHub Issues 是复杂任务规格、验收条件、状态与跨会话交接的权威位置；仓库保留长期设计、ADR 和当前操作指南。
6. **统一入口、按职责就近存放、单一事实源。** 根 docs 提供统一导航与跨项目规范，模块专用说明靠近 owner；可执行契约、测试基线和纯阅读文档分开管理。

7. **证据按用途分层保存。** 仓库保留必要测试基线、不可替代的设计源和精简证据索引；完整发布证明随 Release 长期保存，普通运行输出按 CI 留存策略保存。唯一材料在可靠存放位置落实前保留。
8. **本轮包含确认可重建的本地环境与缓存清理。** 执行前确认用途、再生成命令和活动使用方；真实数据、配置、密钥、未提交研究材料与唯一证据保留。跨 worktree 使用的工具链不能因分支已合并就直接删除。
9. **交付到可合并 PR，由用户合并。** 代理负责验证、可审查提交、独立评审、修复发现、创建并验收 PR；未合并任务标记待合并，合并后按验收结果关闭，不自动合并。

10. **一个总任务，按依赖分批 PR 交付。** 第一批校准当前规范与工作流适配，第二批迁移文档、契约和测试基线，第三批退役历史材料与旧脚本；每批包含引用检查和验收，用户合并后推进依赖它的下一批。本地环境/缓存处置单独记录。

前九项每三项分别由用户在第一、第二、第三轮确认，第十项由第四轮确认。知识归属与保留政策的长期决定见 [ADR 0013](../adr/0013-repository-knowledge-lifecycle.md)。

## 本地清理盘点（只读，未删除）

- 主工作区旧 `.pixi` 约 2.6 GB，是优先核查的可重建环境候选；只有无活动使用方且新工具链与环境可独立使用后才清理。
- 主目录其他可重建候选：`htmlcov` 约 206 MB，pytest/Ruff/import-linter 缓存合计约 9.7 MB。`.hypothesis` 约 9.8 MB 可能保存尚未固化为回归测试的失败样例，须先核验。
- `dist` 约 424 MB 含镜像、Web tar 和 SBOM，`build` 含验收输出；应按证据政策处理，不能直接当下载缓存清理。
- 当前 `.venv` 约 1.2 GB、`node_modules` 约 516 MB，是已准备的现行开发环境，不能因可重建就默认删除。
- 固定 Task、uv 0.12.7 和 Node 24.20.0 的归档/可执行文件目前依赖 sibling `ditto-uv-migration/.cache/toolchains`（约 363 MB）。默认 shell 中 Task 缺失，uv/Node 与仓库固定版本不一致。因此应先让当前仓库不依赖旧 worktree 也能使用声明的工具链；不默认修改机器全局版本。现行 Python 虚拟环境使用用户级 uv managed Python，不能清理该共享解释器。
- 根 `.cache` 约 648 KB 也包含 `.cache/ditto-dev/<identity>/config/config/development/*.env` 和 `state/metadata/metadata.sqlite`；该目录不能整体视为可丢弃缓存。配置内容未读取。
- `.tmp` 约 73 MB 含设计 PDF/DOCX、截图和数据库，唯一性尚未核实；`data` 含真实状态和敏感配置。二者不能按 ignored/临时目录名整批删除。对其中 6 份 PDF、font-test.docx 和 artifact.md 的大小与 SHA-256 核对未发现 tracked 完全相同副本；这不证明业务价值，但足以拒绝直接删除。
- 清理限定为已确认可重建且未被使用的本地环境、缓存和输出；不清理全局共享缓存、不删除其他任务的 worktree 或分支。检查发现跨 worktree 依赖时，先明确或迁移依赖。

## 候选实施分段（待整体确认）

1. **事实与职责校准。** 更新当前架构、CI、宿主说明及导航；给每类现行规范指定唯一 owner 和入口。对不适合 Ditto 的通用 skill 给出适用范围，而非删除用户全局工具。
2. **工作流衔接。** 定义明确的任务范围、可审查变更与验证证据；处理 committed/pending diff 的审查缺口、跨会话交接及评审发现闭环。拆分职责的目标是让宿主 adapter、验证计划和 CI 共享规则有清楚边界，不预设一次性重写 hook 实现。
3. **文档与机器输入分离。** 根 docs 统一导航；局部说明跟随 owner；将混在计划或 archive 内的 SQL 基线、页面合同与原型测试输入迁入对应契约/测试/设计来源位置，并同步消费者。保留真正的设计可编辑源，不根据文件大小假定它与 Markdown 等价。
4. **退役与追溯。** 逐项建立路径、用途、引用、保留理由、目标位置和恢复基线；只有确认没有有效依赖或依赖已迁移，才从 checkout 删除普通历史和失效脚本。已确认退役脚本不作为验证入口执行。
5. **本地可重建状态清理。** 在原工作区核对生成方式、活动使用方和跨 worktree 引用后，清理确认可重建的旧环境、缓存与输出。执行前后记录路径、大小、重建命令和检查结果；真实数据、用户配置、密钥、未提交成果和唯一证据保持完整。
6. **防止再次漂移。** 对当前文档的入口和本地链接、声明的机器输入、skill 源/镜像及实际命令做必要检查；研究/历史叙述不因提及旧技术名称而被当作有效规则执行。普通文档变动保留轻量检查，避免增加全库测试重复运行。

所有分段以可审查、可回退的变更交付；不把文档搬迁、通用技能全局升级和独立业务架构重构混成一次无法归因的变更。

## 三批交付映射

| 批次 | 范围 | 完成条件 |
| --- | --- | --- |
| PR 1：当前事实与工作流 | 上述分段 1–2，以及 skill/镜像和文档入口所需的轻量防漂移检查。把本访谈的任务性内容转入 GitHub 总 Issue/子任务，仓库保留长期规范和 ADR。 | 当前规范不再相互矛盾；Matt 适配避免空审查；复杂任务可根据同一记录交接；本地与 CI 验证范围一致。 |
| PR 2：文件归属与依赖迁移 | 分段 3；按 owner 分离阅读文档、机器输入、测试基线和设计源，并修复引用。 | 迁移清单可追溯，生成器/契约/测试/活跃链接通过；用户可从根入口找到有效说明。 |
| PR 3：退役与收尾 | 分段 4 和其余防漂移检查，移除已被替代且无有效使用方的历史材料、失效脚本。 | 每条删除有依据和恢复基线；没有有效引用、唯一材料或运行行为被破坏；独立评审与 CI 通过。 |
| 本地处置记录 | 分段 5，准备独立工具链后执行已确认安全的本地环境/缓存清理。日志和敏感内容不提交。 | 每个清理路径有用途、无活动依赖证据、再生成命令与清理后检查；主目录固定工具链检查无需 sibling worktree PATH，真实状态与未提交成果摘要不变。 |

每批可以包含多个便于审查的提交。后续若发现必须拆出额外独立 PR 的风险，以总 Issue 记录原因，不扩入独立业务重构；本地处置不要求把机器绝对路径、密钥或运行数据库提交进仓库。

## 候选验收场景（待整体确认）

| 场景 | 需要观察的结果 |
| --- | --- |
| 新会话接手一个明确小修复 | 能从统一入口找到实际 owner、有效命令和必要验证，不被迫创建完整规格/拆票，也不读旧规范当事实。 |
| 复杂任务切换模型或宿主 | 同一 GitHub 任务给出已确认决定、当前提交、未完成事项、验收证据和下一步；不依赖上一段聊天才能继续。 |
| 项目 skill 文本或镜像变化 | 普通说明文档不跑全库；真正影响 skill 结构/同步的变化能在合并前发现漂移。 |
| 文档搬迁或旧目录删除 | 活跃链接、脚本、生成器、测试和证据绑定仍成立；每条退役项能定位删除前的 Git 基线与处置理由。 |
| Claude Code / Codex / ZCode | 配置结构和共享入口自动验收；宿主实际信任/触发与静态配置检查分别记录，不用后者冒充前者。 |
| 工作完成 | 变更范围、评审对象和验证提交一致；成功、跳过、失败与未执行的检查明确区分；不存在未处理的有效评审。 |

既有普通 PR 10–15 分钟目标、现有 runner 额度约束，以及 Task/uv/Bun 和 PIT/契约不变量继续作为基线。文档数量、目录层数和删除行数只能作为盘点指标，不能单独证明优化成功。
