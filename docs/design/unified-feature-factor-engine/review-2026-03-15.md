## 2. 最高优先级问题

以下问题不是“风格偏好”，而是会直接影响系统正确性、控制面一致性或后续可演进性的结构性问题。

### P0-1: 生命周期状态模型已经发生语义漂移

**现象**

- Core 类型系统仍定义 `draft / active / deprecated / archived`：
  - `packages/core/src/ditto_core/engine/materialization/models.py:20`
- 但 publication 流程已经直接写入 `"PUBLISHED"` / `"DEPRECATED"`：
  - `apps/port/src/ditto_port/services/derived/publication.py:232`
  - `apps/port/src/ditto_port/services/derived/publication.py:294`
- SQLite reader / list specs 又同时兼容 `'active'` 与 `'PUBLISHED'`：
  - `packages/datahub/src/ditto_datahub/stores/runtime/derived_sqlite/reader.py:249`
  - `packages/datahub/src/ditto_datahub/stores/runtime/derived_sqlite/reader.py:260`

**问题本质**

系统当前实际上存在两套 lifecycle 语义：

1. `DerivedVersionStatus`
2. publication facade 中的原始字符串状态

这会导致：

- 领域模型失去约束力
- Catalog 中状态语义依赖“读代码猜”
- query / materialize / publish 对“active / materialized / published”的口径不再统一

**设计影响**

这已经不是单个实现细节，而是**根控制面协议失真**。`ADR-034` 的状态机没有被真正编码进统一类型系统。

**建议**

1. 先重做统一的 `DerivedLifecycleStatus`，把 `REGISTERED / MATERIALIZED / PUBLISHED / DEPRECATED` 固化为唯一枚举
2. 移除跨层裸字符串状态
3. 回写 query/materialize/publish/invalidation/research 的状态使用点

---

### P0-2: materialization / publication 没有事务边界，和设计里的“原子提交”明显不一致

**现象**

- materialization 在 Port 层同时做：
  - 物化执行
  - artifact 文件写入
  - runtime metadata 写入
  - manifest / minimal dq / shadow slot 更新
  - `apps/port/src/ditto_port/services/derived/materialization.py:143`
  - `apps/port/src/ditto_port/services/derived/materialization.py:508`
  - `apps/port/src/ditto_port/services/derived/materialization.py:570`
- DataHub SQLite writer 几乎每个方法都立即 `commit()`：
  - `packages/datahub/src/ditto_datahub/stores/runtime/derived_sqlite/writer.py:44`
  - `packages/datahub/src/ditto_datahub/stores/runtime/derived_sqlite/writer.py:66`
  - `packages/datahub/src/ditto_datahub/stores/runtime/derived_sqlite/writer.py:100`
  - `packages/datahub/src/ditto_datahub/stores/runtime/derived_sqlite/writer.py:123`
  - `packages/datahub/src/ditto_datahub/stores/runtime/derived_sqlite/writer.py:150`
  - `packages/datahub/src/ditto_datahub/stores/runtime/derived_sqlite/writer.py:178`
  - `packages/datahub/src/ditto_datahub/stores/runtime/derived_sqlite/writer.py:201`
  - `packages/datahub/src/ditto_datahub/stores/runtime/derived_sqlite/writer.py:239`
  - `packages/datahub/src/ditto_datahub/stores/runtime/derived_sqlite/writer.py:255`

**问题本质**

设计里强调的是“artifact 与 catalog 状态要有一致性协议”，但当前实现是：

1. 先写 parquet
2. 再逐步写 partition / checkpoint / state / run / publication safety
3. 每一步各自 commit

一旦中间失败，就会产生：

- artifact 已落盘但 catalog 不完整
- manifest 已写但 run/state 未同步
- shadow slot 已更新但 candidate 实际没有完整 control-plane 证据

**建议**

1. 把 durable write + catalog mutation 收敛到一个 DataHub transaction boundary
2. Port 只保留 orchestration，不直接承担一致性协议
3. 为 materialization / promote / rollback 明确定义 commit protocol

### P0-3: invalidation cascade 与 ADR-035 的设计差距仍然很大

**现象**

- 当前 invalidation 只是按 `dependency_ref` 拉一跳下游并逐条 repair：
  - `apps/port/src/ditto_port/services/derived/invalidation.py:34`
  - `apps/port/src/ditto_port/services/derived/invalidation.py:85`
- 没有实现：
  - 分层 BFS
  - 最大深度
  - stale / recomputing 状态
  - runtime cycle guard
  - 微批合并

**问题本质**

当前更像“最小 repair 队列”，而不是 ADR-035 定义的 invalidation cascade protocol。

这会直接影响：

- correction / late-arrival 的传播正确性
- 多跳 derived DAG 的行为可预期性
- 后续 realtime / hot layer 接入能力

**建议**

1. 承认当前实现只是 `P0 minimal repair`
2. 不要再把它描述成已完成的 `cascade`
3. 下一阶段独立补：
   - queue protocol
   - traversal policy
   - stale state model
   - cycle/depth protection

### P0-4: research dataset 的“版本绑定”还不是真正的一等契约

**现象**

- `ResearchDatasetFacade` 里 `dataset_spec_version` 是硬编码常量：
  - `apps/port/src/ditto_port/services/derived/research.py:34`
- SQLite 中 `research_dataset_spec` / `research_spine_spec` 都没有 version：
  - `packages/datahub/src/ditto_datahub/scripts/schema.sql:522`
  - `packages/datahub/src/ditto_datahub/scripts/schema.sql:532`
- Snapshot 虽然保存了 `dataset_spec_version`，但来源不是 versioned spec，而是常量：
  - `apps/port/src/ditto_port/services/derived/research.py:273`

**问题本质**

ADR-041 的关键点是：

> `DatasetSnapshot` 必须绑定精确 spec 版本 + 精确输入版本 + 精确源快照

现在只实现了“输入版本冻结”，但**spec 自身没有版本化**，所以 snapshot 还不是完全可复现契约。

**建议**

1. 为 `research_spine_spec` / `research_dataset_spec` 增加 version
2. snapshot 中保存 `(dataset_id, dataset_spec_version, spine_spec_version)`
3. 让 facade 从 spec record 读取真实 version，而不是常量

---

### P0-5: research 默认版本解析会回退到 active_version，可能静默绑定未发布版本

**现象**

- research build 默认使用 `resolve_serving_version()`：
  - `apps/port/src/ditto_port/services/derived/research.py:112`
- `resolve_serving_version()` 在没有 primary online 时，会回退到 `active_version`：
  - `packages/datahub/src/ditto_datahub/services/derived/artifact_reader.py:38`

**问题本质**

这意味着 research snapshot 可能在没有正式发布版本时，直接绑定到“当前 active/materialized 版本”。

对研究可复现性和治理来说，这是危险的：

- 研究集和 serving 版本口径会漂移
- 还未完成 publish gate 的 candidate 也可能进入 snapshot

**建议**

1. research 默认只允许 `primary + online + published`
2. 如果没有 published primary，则必须显式 `version_override`
3. `active_version` fallback 只能留给内部 repair / offline debug，不应用于研究快照默认路径

## 3. 设计层面的问题

### 3.1 根抽象仍然混合了“语义定义”和“执行/治理策略”

`DerivedSpec` 当前同时承载：

- 语义定义：`expression / entity_keys / grain / calendar`
- 执行策略：`materialization_profile`
- 治理/可重复性信息：`operator_versions`
- 派生行为默认：`pit_required / normalization_preset`

位置：
- `packages/core/src/ditto_core/engine/specs.py:48`

这会导致 `DerivedSpec` 越来越像一个“全能配置对象”，而不是纯语义模型。

**建议**

后续把模型拆成三层：

1. `DerivedSemanticSpec`
2. `DerivedExecutionPolicy`
3. `DerivedGovernanceSpec`

至少在代码结构上先拆，不一定一次性改 catalog schema。

### 3.2 类型约束已经退化，和 ADR-032 不一致

实现里：

- `CalendarId = str`
- `GrainId = str`

位置：
- `packages/core/src/ditto_core/engine/specs.py:8`

但 ADR-032 已明确希望这些是显式受限集合。现在的实现虽然 runtime 只支持 `cn_stock` / `1d`，但类型层已经失守。

**建议**

恢复到显式 Literal/Enum，哪怕当前只支持单值，也比 `str` 更符合“控制面契约”。

### 3.3 引擎目录文档已经和现实结构严重失真

`packages/core/src/ditto_core/engine/README.md` 仍然停留在 2026-01-23 的旧引擎形态，没有描述当前 unified derived engine 的目录与职责。

位置：
- `packages/core/src/ditto_core/engine/README.md:1`

这不是小问题，因为现在最核心的新引擎恰好就在这个目录下。

**建议**

尽快重写该 README，避免新人被历史目录误导。

## 4. 实现与设计的主要差距

### 4.1 compile cache 现在几乎没有真正“缓存编译”

**现象**

- `get_or_compile()` 一开始就执行 `self._compiler.compile(spec)`：
  - `apps/port/src/ditto_port/services/derived/compile_cache.py:49`
- L1 cache 只避免重复写 SQLite，不避免重复 compile
- 也没有 L2 SQLite read path

**问题本质**

这更像“compile metadata sink”，不是 `ADR-039` 所定义的 compile cache。

**建议**

1. 先算 deterministic cache key，再查 L1 / L2
2. cache miss 时才 compile
3. compile cache service 应该下沉到 DataHub/runtime store，而不是继续放在 Port

### 4.2 materialization run 在成功路径丢失了真实 compute window

**现象**

- 运行开始时会记录 `plan.compute_start / plan.compute_end`
  - `apps/port/src/ditto_port/services/derived/materialization.py:184`
- 但成功 finalize 时又把 `compute_start / compute_end` 写回 `request.request_start / request.request_end`
  - `apps/port/src/ditto_port/services/derived/materialization.py:348`
  - `apps/port/src/ditto_port/services/derived/materialization.py:444`

**问题本质**

这会抹掉：

- lookback 扩展窗口
- invalidation 向前回退窗口

从而让 run metadata 失去 audit/debug 价值。

**建议**

把 `DerivedExecutionPlan` 贯穿到 finalize，run record 始终写真实 compute window。

### 4.3 `_prepare_input_frame()` 对缺失依赖采用 fallback alias，语义过于危险

位置：
- `apps/port/src/ditto_port/services/derived/materialization.py:724`

当前逻辑会在依赖列缺失时，把第一个非 key 列 alias 成缺失依赖列。

这会把“输入装配失败”静默降级成“拿错列继续算”，对因子/特征引擎来说风险非常高。

**建议**

1. 缺失依赖直接 fail fast
2. 只允许显式 alias mapping，不要默认 fallback

### 4.4 query / compare contract 已落地，但 compare_sources 仍不是真正的 source abstraction

位置：
- `packages/datahub/src/ditto_datahub/services/derived/query_service.py:101`

当前 `compare_sources()` 虽然接收 `compare_sources`，但实际始终比较：

- `resolve_serving_version()`
- `resolve_offline_version()`

而不是基于真正的 source backend abstraction 选择不同源。

在 artifact-first 阶段这可以接受，但需要明确它是：

> compare version resolution
而不是
> compare heterogeneous sources

否则后续接 QuestDB/Kvrocks 时会继续混淆。

## 5. 分层、抽象与模块划分问题

### 5.1 Port 层承担了过多 DataHub 职责

当前 Port 层直接处理大量持久化细节：

- 写 artifact parquet
- 写 research snapshot 文件
- 写 metadata json
- 组装 manifest / diff / certification payload

典型位置：
- `apps/port/src/ditto_port/services/derived/materialization.py:488`
- `apps/port/src/ditto_port/services/derived/research.py:184`
- `apps/port/src/ditto_port/services/derived/publication.py:44`

这与设计里“Port 编排、DataHub 存储与控制面”的职责边界不完全一致。

**建议**

把以下能力下沉：

1. artifact writer / reader
2. research snapshot store
3. publication compare persistence / report store

Port 保留：

1. request -> orchestration
2. policy selection
3. flow / DI wiring

### 5.2 服务对象过大，抽象层级已经开始失控

当前文件体量：

- `DerivedMaterializationService`: 1033 行
- `DerivedPublicationFacade`: 739 行
- `ResearchDatasetFacade`: 571 行

这说明当前切分是按“功能阶段堆进一个类”，而不是按“稳定职责边界”切分。

**建议**

至少拆成：

1. `DerivedMaterializationOrchestrator`
2. `DerivedArtifactPersistenceService`
3. `DerivedPublicationEvidenceService`
4. `ResearchSnapshotBuilder`
5. `ResearchSnapshotStore`

### 5.3 compile cache 命名和落点都不合理

位置：
- `apps/port/src/ditto_port/services/derived/compile_cache.py:1`

问题有两个：

1. 它不在 Port 的职责边界内
2. 当前实现更像“compile metadata persistence”，不是完整 cache

**建议**

迁移到 DataHub/runtime，并把名字改成：

- `CompiledExpressionCacheRepository`
- `CompiledExpressionCacheService`

## 6. 最佳实践与工程化问题

### 6.1 rolling window 语义需要尽快和 PIT 规则对齐

位置：
- `packages/core/src/ditto_core/engine/expression/codegen.py:95`

当前 `ts_mean / ts_sum / ts_std / ...` 直接使用 rolling API，没有显式 left-closed / shift 语义。

这在统一引擎里会引出一个必须尽快明确的问题：

- 当前定义到底是“包含当期”还是“严格只看已知过去”？

如果项目 PIT 规则要求避免当前 bar/day 泄漏，那么这里需要统一裁决，而不是继续模糊。

### 6.2 query facade 里的 `RuntimeMode` 还是空 seam

位置：
- `apps/port/src/ditto_port/services/derived/query_facade.py:82`

现在 `resolve()` 之后立即丢弃。它作为 Phase seam 可以保留，但需要明确：

- 要么下个阶段真正消费
- 要么删掉，避免假抽象

### 6.3 DataHub record model 仍大量使用原始字符串

典型位置：
- `packages/datahub/src/ditto_datahub/models/derived.py:72`
- `packages/datahub/src/ditto_datahub/models/research.py:13`
- `packages/datahub/src/ditto_datahub/models/publication_safety.py:52`

当前 record 层几乎全部用 `str` 承载状态/角色/阶段，导致语义校验进一步被推迟到运行期。

这在 runtime record 层是常见折中，但当前跨层字符串已经太多，建议在 service boundary 及时恢复到 enum/value object。

## 7. 当前总体评价

### 7.1 优点

1. 架构主线是对的，且没有明显偏离真相源
2. DSL / query / materialize / research / publication 的主链已经基本成形
3. 测试覆盖从 unit 到 targeted integration 已经具备工程雏形
4. 没有引入明显违背现有栈的技术选型

### 7.2 当前核心风险

1. **控制面语义不统一**
2. **Port/DataHub 边界开始塌陷**
3. **工作树实现超前于提交历史，事实状态分裂**
4. **很多能力“能跑通”，但还没有被封装成稳定协议**

### 7.3 结论

当前 unified-feature-factor-engine 已经跨过“是否能做成”的阶段，真正的问题是：

> **能跑的功能越来越多，但统一控制面、层边界和长期可维护抽象还没有同步跟上。**

如果现在继续横向扩功能，而不先收敛这些问题，后面进入 hot layer / realtime / 多市场时返工成本会明显增大。
