# ADR-011: 盘中微批量处理模式（Intraday Micro-Batch Mode）

**状态**: 已修订（2026-03-10）

**修订说明**: 本 ADR 已大幅修订，移除了流式引擎概念（ReactiveStateEngine、CrossSectionalEngine），存储架构拆分到 [ADR-028](adr-028-questdb-hot-tables.md)。

---

## 背景

盘中实时因子计算是量化交易的核心需求。与流式处理（逐事件触发）不同，Ditto 采用**微批量处理模式**：

- **批量间隔**：按固定时间窗口（如 1 分钟、5 分钟）批量处理
- **统一引擎**：使用同一套 Polars 表达式引擎，不引入独立的流式引擎
- **状态管理**：通过 Kvrocks 维护滑动窗口状态，而非内存流表

这种方式在延迟和复杂度之间取得平衡：延迟可控（秒级），实现复杂度低。

---

## 盘中场景定义

| 场景 | 数据频率 | 延迟要求 | 典型因子 | FactorServeMode |
|------|---------|---------|---------|-----------------|
| **分钟级因子** | 1min/5min/15min | < 1s | 分钟动量、分钟波动率、资金流 | SERIES |
| **实时信号** | 1min 快照 | < 1s | 盘口失衡、大单监测、价格冲击 | SERIES |
| **日内策略** | 5min | < 5s | 日内趋势、反转信号、量价背离 | STATE |
| **风控监控** | 1min | < 2s | 持仓风险、敞口监控、异常检测 | STATE |

## 与流式处理的区别

| 特性 | 流式处理（已废弃） | 微批量处理（当前方案） |
|------|-------------------|----------------------|
| **触发方式** | 逐事件触发 | 定时批量触发（1m/5m） |
| **状态引擎** | ReactiveStateEngine | 复用 Polars + Kvrocks 状态 |
| **截面计算** | CrossSectionalEngine | 微批量截面聚合 |
| **延迟** | < 100ms | < 1s（可接受） |
| **复杂度** | 高（独立引擎） | 低（复用批量引擎） |
| **一致性** | 难保证 | 易保证（批量语义） |

**决策理由**：
1. **复杂度可控**：不需要独立的流式引擎，复用 Polars 批量引擎
2. **一致性保证**：批量语义天然支持精确一次处理
3. **延迟可接受**：1 分钟级因子对 1 秒级延迟完全可接受
4. **运维简单**：无需管理流式引擎的状态和检查点

## 存储技术选型

> 存储架构已拆分到 [ADR-028: QuestDB 热表与物化视图 DDL](adr-028-questdb-hot-tables.md)

### 存储层职责

| 存储层 | 技术选型 | 职责 | 详细设计 |
|-------|---------|------|---------|
| **热层** | QuestDB + Kvrocks | 盘中实时查询、状态管理 | ADR-028, ADR-031 |
| **冷层** | Parquet | 历史归档、离线分析 | main-design.md |

### QuestDB 核心优势

1. **O3（Out-of-Order）原生支持**：延迟数据自动重排序
2. **DEDUP UPSERT**：自动去重，历史修正数据直接替换
3. **SAMPLE BY**：原生降采样聚合，无需写 ETL 任务
4. **高性能**：550 万行/秒写入，16 亿行聚合查询 0.15s
5. **极简部署**：单二进制，零外部依赖

### Kvrocks 优势

- Redis 协议兼容：可用 redis-cli 调试，redis-py 客户端成熟
- 基于 RocksDB：持久化好，crash 后自动恢复
- 单机部署：启动成本低，无需 Redis Cluster
- 多进程共享：多个 worker 可共享状态

## 状态管理

> 详见 [ADR-031: State Snapshot ABI](adr-031-state-snapshot-abi.md)

### Kvrocks Key 设计

| Key Pattern | 内容 | 生命周期 |
|-------------|------|---------|
| `state:feature:{factor_id}:{instrument_id}` | 因子快照（HASH/BLOB） | 2-7 天 TTL |
| `state:signal:{strategy}:{instrument_id}` | 最新信号 | 当日到 3 天 |
| `state:risk:{account}:{instrument_id}` | 风控状态 | 无 TTL（权威状态） |

### 状态初始化（STATE 因子）

```python
# 盘前：从 Parquet 初始化 STATE 因子快照
async def initialize_state_factor(spec: FactorSpec) -> None:
    """盘前初始化 STATE 因子状态"""

    # 1. 从 Parquet 读取历史数据
    historical_data = await parquet_reader.read_factor_series(
        spec.id,
        lookback=spec.lookback,
    )

    # 2. 计算初始快照
    snapshot = compute_state_snapshot(spec, historical_data)

    # 3. 写入 Kvrocks
    await kvrocks_writer.write_state_snapshot(
        spec.id,
        snapshot=snapshot,
        strategy=spec.state_snapshot_strategy,
    )
```

## 存储成本估算

### 基础数据规模

| 参数 | 数值 | 说明 |
|------|------|------|
| 标的数量 | 5,000 | A股股票 |
| 交易日/年 | 250 | 中国股市 |
| 分钟/交易日 | 240 | 4小时 × 60分钟 |

### QuestDB 存储估算

| 数据层级 | 保留期 | 每日新增 | 压缩后 |
|---------|-------|---------|-------|
| 分钟级 | 120 天 | 120万行 | ~860 MB |
| 聚合级 | 180-365 天 | ~2万行 | ~20 MB |
| **合计** | | | **~1 GB** |

### Kvrocks 存储估算

| 状态类型 | 数量 | 压缩后 |
|---------|------|-------|
| 因子快照 | 5000×10因子 | ~15 MB |
| 信号/风控 | 临时 | ~2 MB |
| **合计** | | **~17 MB** |

| 组件 | 磁盘建议 | 年度增长 |
