# 工程简洁性：最小必要复杂度基准

日期：2026-09-15。决策来源：[业界基准：哪些复杂度能换来可验证的质量](https://github.com/cosmos-arc/ditto/issues/176)。

范围：一手实践研究；个人工作站、研究与 Agent 扩展能力同等优先。本文提出判断依据，不代表完成源码审计，也不直接批准删除或重构。

## 来源事实

- Google 代码审查指南要求解决当前已知问题，警惕尚无需求的泛化；测试应适合改动，能在行为损坏时失败，测试自身也有维护成本。[代码审查](https://google.github.io/eng-practices/review/reviewer/looking-for.html)
- Google SRE 区分问题本身的必要复杂度与实现引入的偶然复杂度；提倡小 API、清晰模块边界、删除无用代码，并允许具有明确寿命的探索代码。探索代码降低验证要求的前提是不交付生产或用户。[Simplicity](https://sre.google/sre-book/simplicity/)
- SRE 可靠性目标应围绕关键用户活动，先选相关且容易测量的指标，再逐步改进；组件请求成功不能直接代表用户流程成功。[Implementing SLOs](https://sre.google/workbook/implementing-slos/)
- SQLite 提供 Online Backup API，为运行中的数据库生成一致快照；并发写入可能令备份重启，频繁重启可能妨碍完成。存在备份接口不等于项目已具备恢复能力。[SQLite Backup API](https://www.sqlite.org/backup.html)

## 对 Ditto 的推论与决策依据

1. **先找重复责任，再压缩代码。** 同一业务规则宜有一个权威实现，其余层负责转换或验证。只有一个实现的 Protocol、较多文件或较高 LOC 都不是删除证据；应先查它是否隔离领域、外部 I/O、测试替身或审批权限。合并后若消费者更难理解，便没有变简单。
2. **研究能力以可证伪问题证明价值。** 不要求研究与 Agent 功能每天使用；要求说明问题、输入与评估方式、成本上限，以及保留、毕业或退出条件。缺少这些依据的通用插件层、可配置流程和备用路径可列为延后候选。会接触用户或真实状态的实验仍须守住相应安全边界。
3. **验证按风险选最小充分范围。** 纯文档、纯移动与资金/PIT/权限变化不应套用相同检查规模。合并重复门禁前核对它们捕获的故障与执行阶段；保留能发现独有风险的检查，不用测试数量或覆盖率单独证明质量。
4. **优先补用户可感知的证据。** 候选是少量贯穿 UI、状态和结果的流程：研究可重现、Agent 受控执行、Paper/手工账本正确。先查现有证据缺口，再补可重复验收；无需先建通用可观测平台或照搬企业级值班制度。
5. **恢复优先于更多后台机制。** 核查备份完成条件、数据库与外部产物的对应关系、恢复步骤及一次隔离恢复演练。SQLite 单库快照不保证多个存储的一致性。是否需要更复杂协调，要由实际状态关系决定。

## 下一步的最小问题

每项候选只需回答：谁使用或研究什么；移除后损失何种独有保障；保留与简化各有什么维护成本；用什么最小验证作出决定。优先处理无消费者且无研究问题的机制、重复权威实现和恢复证据缺口。具体删减、收益排序及工程投入由后续决策票结合当前代码确认。
