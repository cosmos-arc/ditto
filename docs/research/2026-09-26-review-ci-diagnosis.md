# Ditto 多轮 CR 与验证周期诊断

日期：2026-09-26。状态：**研究结论与待讨论草案，不是已生效流程**。

## 结论

目前证据支持三个问题同时存在：首次实现遗漏重要语义，首次审查和修复未按整类风险
闭合，以及验证流程把每一次往返放大为长等待。不能简单归因于“实现模型不行”或
“CR 太苛刻”。重点 PR 的后续发现里有真实 PIT、资金/账本、来源及身份缺陷，也有
修复引入的回归；删掉审查或把两轮设为强制合并上限，会丢掉实际保障。

最有把握先改的是：**失败原因先复核、本地和 CI 验证口径一致、首审覆盖完整语义、
修复围绕根因及消费者集中处理、复审检查修复影响、非阻断建议明确分流**。单轮远端
CI 已比 9 月 12 日报告快；更大的浪费来自多轮反馈与重复验证，不能只盯 runner。

## 先统一量度

这些是本报告的分析用语，不是投资领域词汇，不新增根 CONTEXT.md。

| 名称 | 本次定义 | 不能混作什么 |
|---|---|---|
| Finding | 一条独立的缺陷主张；真假和是否阻断分别判断 | 一条评论、一个 P1/P2 标签 |
| 审查轮次 | 机器人实际审查的不同 commit SHA，作为可观察代理指标 | GitHub review 对象总数；作者回复也会创建对象 |
| 修复批次 | 围绕相关根因的一组修改和验证 | 每个 commit；一个批次可包含多提交 |
| 首次实现缺陷 | 首次送审提交已存在的实质问题 | 每个后轮 finding 都是新引入 |
| 首审遗漏 | 首次已存在但后续才发现的问题 | 审查工具误报 |
| 修复回归 | 相邻修复差异引入、可追到新代码的问题 | 首审遗漏的重新发现 |
| 阻断发现 | 当前范围内成立，影响需求、不变量或必要工程质量 | 所有可改进点 |
| 可合并时间 | 最新内容的适用门与有效阻断处理完毕的时间 | PR 创建时间；CI 单独绿灯 |
| 单轮反馈时间 | push/提交到首个可行动结果及适用门结束，分别记录 | Git commit 时间到 review 的纯模型运行时间 |

时间区间重叠要取并集；不能把 CI 累计分钟、多个并行 job 分钟与 PR 墙钟直接相加。
轮数只能定位异常，不能单独判断责任、有效率或模型能力。

## 实现质量：有实质缺陷，但问题在语义闭合

### 1. 测试量大，没有覆盖新行为的关键场景

#304 初次交付会话报告 16,869 项测试通过、双轴审查处理完毕，后续仍补了 16 个修复
提交。修复涉及实际 ETF 留存数据格式、D/D+1 可见时间、账本并发、审批绑定和下单
约束。#308 首次本地完整门与双轴审查通过，GitHub 随即发现停牌、退市和历史代码映射
问题。它们不靠扩大通用测试数量解决，需要正确的领域场景及真实消费者。

因此首轮实现质量不足是成立的；更准确的说法是**端到端事实、边界和不变量没有在
首次交付形成闭环**，不是“没跑测试”。本次没有受控模型对比，不能推断换更强模型
必然解决，也不能给出不同模型的缺陷率。

### 2. 局部修复容易继续留下同类问题

#308 的来源、生命周期、日历权威、快照修订和证券隔离问题连续出现。同一类语义
在价格、因子、停牌状态、交易日历、日周月聚合、空图和导出中有多个消费者。
只修评论所指的 if 分支，再加对应测试，可能留下同类的其他路径。

推荐在首审和修复时沿这一条真实链核查：请求与证券身份 → cutoff 与准入 → 请求修订
及 source/schema → 可见价格/状态/日历 → 生命周期与预期日期 → 周月聚合 → UI/导出。
不是再造清单平台；用本票已有测试和短小场景表，将相关反例一次补齐。

### 3. 修复本身也会制造新缺陷

#304 一次 account 隔离修复改变 run_id，却未同步 SignalPackagePublisher 的既有校验，
下一轮真实 handoff 被拒绝；这是可追到修复 diff 的回归。#308 的逐交易日映射核查
引入逐日数据库查询，后续发现数千次点查，再改为批量读取；这是正确性修复的性能
后果。会话还记录日历生命周期修复后出现空窗口倒置查询。

修复接受前必须检查所有调用者及受影响入口，不能自动把 AI 给出的修改当作正确
解决方案。新回归和旧遗漏分别记账，才知道该改首轮实现还是修复方法。

## 审查角度：审查有效，覆盖与收敛方式不足

### 1. “规范 + 规格”覆盖不等于完整正确性覆盖

当前通用 code-review 把 Standards 与 Spec 分开；规范轴另带 smell baseline。
这是有用的视角，但抽象/命名检查、按 Issue 字面逐条核对，仍可能遗漏时间、数据格式、
并发、失败恢复及调用者之间的交互。并行两个 reviewer 也不会自动覆盖端到端事实。

建议保留需求与规范两个视角，但将本票最重要的不变量与真实入口交给明确的审查
责任人。报告标明检查了什么、未检查什么；“没有发现”只描述已检查范围。

### 2. 后轮大量发现说明首轮问题没有被成批暴露

123 条 finding 中只有 13 条在首轮出现，说明整个审查/修复系统在渐进地探索风险。
这一分布本身不能证明审核越界，更不能证明机器人故意每次只报两条；本次没有读取
自动 reviewer 内部提示词或运行轨迹。可操作改进是：首次固定内容，先看主要行为、
数据/身份/并发边界，再看细节；相关发现汇总后集中修复。

重大缺陷可立即反馈，不必为“一次说完”延迟。第三轮仍出现阻断时，先解释是首审
遗漏、修复回归、需求变化还是不成立，然后决定回查整类风险或由维护者裁决。

### 3. 不应把所有发现升级为必须修复

目前逐项抽查证实多个核心缺陷，**没有证据支持把整体主因定为大量无效挑刺**。
但现有交付规则没有充分写明真假、阻断性、已拒绝发现及复审边界，容易把普通建议
变成新一轮全量修复。全局 skill 的 smell baseline 明确是判断性启发，不是硬标准；
不能把它或个人写法偏好直接当成当前需求。

推荐每条阻断给出位置、触发输入/路径、后果、依据和证据；无效意见可用反证关闭，
可选建议注明不阻断，新需求进入后续 Issue。共享根因涉及更多文件不自动等于越界；
为保证本票 PIT 或账本正确而修共享读取器可能必要，新增无关产品能力则应分开。

Google 的标准是平衡推进与整体代码健康，不要求完美；事实优先于偏好，教育/细节
建议应标明可选。[Google 审查标准](https://google.github.io/eng-practices/review/reviewer/standard.html)、
[评论严重性](https://google.github.io/eng-practices/review/reviewer/comments.html)。

## CI 与本地验证：具体浪费已经可定位

### 1. #307 的确定性红灯被反复送到远端

CI 日志显示 #307 连续 11 个 runs 的 Web 单测均为 1,977 passed，却因 API 分支覆盖率
89.95% < 90% 失败。这不是 11 个新行为 bug，也不是靠重跑可消除的 flaky。

根 Task 中 `check-web` 运行 `web-static + web-test`，CI 的 `web-quality` 运行
`web-static + web-coverage`。`task check` 和 pre-push 可以绿，而 CI 覆盖率仍红。
完整日志及 run 链见 CI 审计。另有独立的 datetime-local 输入和原型精度失败，不能
把全部失败都归为覆盖率。

第一优先是复用 CI 的同一个覆盖率入口，找到缺失的真实分支并补必要行为测试；在
失败门本地已复核前，不再发同类“应该绿了”的候选提交。不得降阈值或增加无意义
断言来迎合百分比。日常每次编辑仍可跑快速测试，送审/已知失败复核才用对应门。

### 2. 本地完整检查、pre-push、远端形成重复串行成本

本地会话的已完成命令证据：

- #304 初次实现 `task check` 11.22 分钟，之后成功 `git push` 14.41 分钟；push 包含
  hook 和网络，不能把全部都称作冗余测试。
- #307 最后接手 turn 用时 218.49 分钟，其中七次长成功 push 分别约 10.08、8.70、
  9.66、6.99、7.37、6.96、6.41 分钟，合计约 56.2 分钟；另一次显式 `task check`
  6.53 分钟。其余时间含诊断、修复、专项验证、CR/CI 等待，不可全部归为等待。
- #308 反复出现“局部测试/双轴复审 → pre-push 完整 check/system/PIT → CI → 新 CR”
  的会话记录；这轮尚未结束，不给完整总成本。

pre-push 实际比较远端 ref 到 HEAD，**已有增量范围选择**，不是始终比较整份 PR。
但跨栈、高风险路径仍会选择宽验证。不要基于错误假设重写选择器。

最小起步是取消同一最终内容上不必要的手动全量复跑，让已有门只承担一次本地完整
验证；小修复先跑专项和廉价检查。若要进一步将重的全库验证集中到远端、pre-push
只保留快速必要检查，需要明确修改验证分工，不能临时 SKIP/no-verify。先不回加
receipt 或跨提交测试结果缓存。

### 3. 廉价失败暴露得太晚

`task check` 顺序先完成后端再查 Web。两个 #308 的本地失败日志先跑过 15,785 个
Python 测试（约 138 秒），之后才报 Web TS2352 / TS4111。至少这两次，可先对改动
Web 文件运行类型检查来提前发现，修正后再付完整门成本。

建议先运行两栈相关类型、格式、契约等廉价检查，再进入重测试；不在同机开多套完整
验收争抢资源。已知失败门优先，不需要另建流水线框架。

### 4. 远端单轮耗时和总轮数要一起优化

CI 审计的六个重点 PR 共 84 轮，其中 83 轮已经结束；run 创建到 job 最后完成的
中位数 11.80 分钟、p90 12.88 分钟，初始启动等待中位数 3 秒，主要不是 runner
排队。后端分片后的 coverage/PIT 串行汇总及 macOS smoke 是当前主要路径。
83 轮中 65 轮最后完成的是后端汇总，18 轮是 macOS；最慢分片中位数 8.35 分钟，
后端汇总 job 中位数 2.81 分钟，macOS job 中位数 10.24 分钟。job 指标不含前置等待，
两条并行路径不能相加为单轮时长。
旧报告的 backend 两分片约 14 分钟已经不是当前结构，不能按旧结论采购算力。

#304 17 轮 CI 全成功却持续 CR 返工；#308 在采样时 20 次成功加一次进行中。
这说明“CI 稳定绿”没有覆盖全部领域语义。将单轮从 12 分钟压到 9 分钟有价值，
但若仍二十轮往返，总周期仍很差。CI 累计分钟只能描述资源/等待规模，不能直接
解释净墙钟收益。

DORA 建议快速可靠反馈在数分钟内，约 10 分钟是快测试层上限参考；完整 E2E 仍必要。
不能把该目标当作删除 Ditto 平台、PIT、安全或契约门的理由。
[DORA CI](https://dora.dev/capabilities/continuous-integration/)。

### 5. 文档口径也有漂移

PR 模板仍列旧包名、每次 `task check`、固定覆盖率数字和简化 PIT checkbox，与当前
风险验证和机器事实源不一致。CI 的 main push 已采用部分检查，README/Harness/ADR
0011 仍写 main 全量，需核对变更来源并统一实际已授权政策；不能悄悄用旧文字恢复
重检查，也不能把部分 main run 当作完整证明。

当前 ruleset 已核实：审批数为 0、要求线程解决、strict `CI gate`。未解决评论会
阻止合并，但并非固定多名 reviewer 审批导致等待。规则本身不要求意见都必须采纳；
无效 finding 可以给证据后解决，真实缺陷必须修复。无需先关闭保护。

## 推荐的最小流程草案

1. **开工明确一条可验收行为。** 复杂票只补争议决定及关键场景，不重做全套文档。
   先查真实数据/DTO/DI/存储/消费者；跨栈生成物与必要消费者保持原子交付。
2. **送审前完成最小充分证据。** 正常路径、关键拒绝路径、PIT/身份/重试或并发边界
   按本票风险选取；已知 CI 红灯先复核。静态门先暴露，完整验证避免重复手跑。
3. **首审一次覆盖关键语义。** 固定基线与 SHA；保留两轴来源，明确端到端正确性
   责任。机器已检查的格式不再人工重复；smell 是建议而非自动阻断。
4. **一个整合者核验发现。** 判真假、是否阻断、是否同根因；保留反证及未测范围。
   同类缺陷一起检查所有消费者，集中成一个修复批次，不逐评论盲改盲推。
5. **修复复审以新增差异及影响为主。** 检查原发现闭合和新回归；修复改变来源、
   时间、资金或公共边界时扩大到相关语义，不因“增量”漏审受影响旧代码。
6. **第三轮触发归因和裁决。** 没有固定放行上限。发现新的真实关键缺陷继续修；
   重复遗漏则回查整类场景，偏好/新需求分流，争议由维护者决定。
7. **合并看最终内容证据。** 当前提交适用 CI、有效阻断和审查状态一致；有可能
   产生发现的自动审查仍在运行时，不能只因 CI 绿就宣称全部审查完成。

该路径与 Google 的小而自洽变更、先审总体设计、评论分级一致，属于对 Ditto 的
适配建议，不是业界统一的“一审一改一复审保证成功”。
[Google Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)、
[DORA 小批量](https://dora.dev/capabilities/working-in-small-batches/)。

## 执行顺序与验收

| 优先级 | 最小工作 | 验收依据 | 风险/决定 |
|---|---|---|---|
| 先做 | 统一已知失败门的本地/CI入口；廉价静态失败先检查；纠正模板与当前政策冲突 | 同一个确定性失败可在 push 前复现；修复真实分支后对应门通过 | 不降阈值，不变更服务端保护 |
| 同时 | 将阻断依据、首审范围、修复批次和复审影响写入现有交付约定 | 后轮 finding 可区分旧遗漏/回归/新需求/误报；没有以零发现取代证据 | 草案需维护者确认，不修改用户全局 skill |
| 试行 | 在下一批 5 个可比 PR 记录最少指标 | 比较总交付时间、有效返工批次、确定性红灯重复次数、合并后缺陷 | 5 个仅是试行起点，不够统计因果 |
| 然后 | 消除重复全量验证；若仍慢，明确 pre-push/远端分工 | 最终提交仍有完整适用证明，本地等待下降 | 涉及验证政策调整，先确认精确边界 |
| 最后 | 优化后端 coverage/PIT 后置及 macOS job 的实际步骤 | 同类 full runs 的 p50/p90下降，无缺失/取消/错误跳过 | 保留覆盖合并和身份合同；测量后再选算力 |

最少记录五项即可：开始实现到可合并；有效修复批次；首审遗漏与修复回归；同一
确定性 CI 失败的重复提交数；提交到首个可行动结果及最终门结束。附合并后发现
作为质量护栏。用 Issue 评论和现有 API，先不建 dashboard、评分平台或多模型投票。

本轮尚不确定全部 finding 的有效率、各模型责任占比、全部本地验证区间以及自动
review 内部限额/配置。不能承诺“效率提升 X%”；完成试行后再用同口径数据判断。
