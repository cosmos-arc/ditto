- 日期：2026-09-12。数据来源：GitHub PR/issue/run 只读 API（#133 回溯基线），口径见下。
- 目的：把「harness 精简是否变好」的证据从结构指标（文件数、行数、CI 时长）升级为结果指标；为后续每项 harness 改动提供准入证据。

## 回溯观察（PR 级代理指标，非任务级结论）

1. **人工介入极少且集中**：仅 #135 有真实人工活动（8 条 review + 1 条 issue 评论），
   其余批次人工评论为零、review 全部来自 Codex 自审。当前模式是「agent 自审 + 人工抽查把关」。
2. **工具链迁移是返工重灾区**：#109 为 33 commits、29 次 CI、26 次非成功、1.7 天；
   印证 9 月 6 日评估「迁移不消除流程成本」的判断。
3. **三连批流水化吞吐最高**：#124–126 各 21 分钟–2 小时合并、零人工介入；
   319/151 文件的大迁移拆批后风险未上升（红灯各 ≤1 次）。
4. **小 PR 一次通过率高**：#110/#125/#128 一次绿；红灯集中在重写 CI 的 #96 与
   多轮 review 的 #135（后者含一次已定性的瞬时基础设施失败）。
5. **挂起时长与人工把关正相关**：仅有的两个多轮 review PR（#135 近 3 天、#109 1.7 天）
   占据时长前两名——等待人工是主要挂起来源，不是验证本身。

## 前瞻对照协议

后续 harness 相关实施任务（含 #130 剩余批次）在 Issue 交接评论按以下字段记录；
每完成 3–5 个任务在本文档追加一轮对照小结：

| 字段 | 定义 | 口径 |
|---|---|---|
| 验收一次通过 | 合并门首次全绿即合并（重跑基础设施失败除外，须注明） | PR check runs |
| 返工提交数 | PR 内 review 修复/fix 类 commit 数 | git log |
| 人工干预次数 | 维护者评论、review、手动操作次数（bot 除外） | PR/issue API |
| 重复验证次数 | 同一内容触发的完整验证次数（本地 check + CI run） | 本地命令 + runs |
| token 用量 | 任务全会话消耗（host 记录值，不含子代理细分则注明） | host 统计 |
| 实际耗时 | 首条任务记录到 PR 创建的墙钟时间 | 时间戳 |

首份对照记录随 #132/#133/#134 批次的交接评论落档（本协议的自举样本）。

## 与 Stop hook 的联动

「Stop 维持仅提示」的再评估条件已写入 [agent-harness 说明](../engineering/agent-harness.md)：
出现完成声明与验证状态脱节的真实案例（如 Stop 通过但合并门拦截未验证变更）时，
先立条件阻断提案并附案例证据，再改实现；不按业界潮流直接升级。

## 局限

- PR 级代理指标不能区分单任务内的多轮探索；任务级字段从前瞻协议起才有。
- cancelled run 与真实失败混计，回溯表中的「失败」偏高（#109 尤甚）。
- 单维护者场景，「人工干预」即用户本人；多人语境不适用本基线。
