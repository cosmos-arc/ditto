# PR 审查返工与 CI 反馈效率：一手资料研究

研究日期：2026-09-26。状态：诊断用来源笔记，建议尚未成为仓库规则。

本文区分三类材料：供应商产品机制、工程实践建议、研究推断。它不证明 Ditto 当前
哪一类问题占比最高；归因需要 PR 的逐条发现、修复差异、CI 日志与时间线。
按[知识生命周期](../engineering/knowledge-lifecycle.md)，研究保留在此；确认后的
执行安排进入 Issue，只有长期取舍已明确时才提炼 ADR。

## 可直接采用的判断

多轮 CR 不是实现质量差的充分证据。每轮都找到可复现缺陷，才主要指向实现或首次
审查遗漏；每轮扩大需求、重复已解释问题、把个人偏好升级为阻塞，才指向审查治理。
真实缺陷和无效发现都可能通过串行等待、重复全量验证放大交付时间。这是本次研究的
分析框架，不是外部研究已经替 Ditto 做出的结论。

业界资料支持更小的变更、更清晰的阻塞标准、更快的反馈和可靠自动检查。它们不支持
“反复跑 AI 审查直到零发现”作为充分完成条件，也没有给出适用于所有项目的“两轮后
必须合并”标准。可以为第三轮设置归因和人工裁决触发点，但不能据此放过已证实缺陷。

## 来源与适用边界

### 1. Google：审查以代码健康的净改善为准

来源：[The Standard of Code Review](https://google.github.io/eng-practices/review/reviewer/standard.html)。

Google 要求审查者权衡推进与质量：当变更明确改善整体代码健康时，通常应批准，即便
仍有可打磨之处。技术事实优先于个人偏好，未进入风格规范的纯样式选择不应假装成
硬性标准；不重要或教育性的建议应明确为非必须。冲突不应靠无限评论等待解决。

边界：这是 Google 的工程政策，不是对任何风险都允许“差不多”的授权；原文也不
允许提交明确降低代码健康的变更。Ditto 的资金、PIT、安全、契约不变量仍然是实质标准。

对 Ditto 的推断：阻塞发现必须指出违反哪条已确认需求、不变量或可验证工程原则。
“我更喜欢另一种写法”“以后也许需要扩展”默认非阻塞；可维护性问题可以阻塞，
但必须说明当前维护成本或实际失败路径，不能只贴抽象原则标签。

### 2. Google：将评论的意图和严重性显式标记

来源：[How to write code review comments](https://google.github.io/eng-practices/review/reviewer/comments.html)。

该指南要求解释原因，鼓励简化，并将必要修改与建议区分。Nit、Optional、FYI 等标签
能防止作者把所有评论都理解为本轮必须修复。作者负责选择解决办法；审查者不必把
每条发现扩展为完整的新设计。

边界：标签本身不证明发现有效；严重性与真实性应分别判断。

对 Ditto 的推断：每条发现最少记录“触发条件、实际后果、依据、必须/可选”。AI 给出
高优先级不等于已确认高风险。已有证据反驳的发现应记录理由关闭；未知则保留为
需要补证的疑问，不自动加入实施范围。

### 3. Google：先看整体方向，再看细节

来源：[Navigating a CL in review](https://google.github.io/eng-practices/review/reviewer/navigate.html)。

Google 建议先判断变更是否应该存在、主要设计是否合理，再按顺序审查其余部分。
重大方向问题应尽早反馈；如果经常写完后才被告知方向不对，应该改进实施前沟通。

边界：尽早发重大问题不要求等待完整审查结束；不能为“一次说完”延迟首个关键反馈。

对 Ditto 的推断：复杂工作在实现前对齐少量有争议的范围、边界与验收，不新增日常
会议或全任务评分。首轮 CR 优先完成端到端语义与风险审查，避免先打磨小细节，下一轮
才发现主流程错误。首轮发现汇总后集中修复，重大风险可以提前打断。

### 4. Google：小变更是概念自洽，不只是行数少

来源：[Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)。

小而聚焦的变更更易全面审查、合并与回滚。一个 CL 应做一件事，包含相关测试及理解
所需上下文，合并后系统继续可用。新增 API 应有消费者，避免拆出闲置接口。没有统一
行数阈值；生成内容、删除、分布文件数都会影响实际审查负担。大规模重构通常与功能
修复分开。

边界：行数门槛只能提示，不能替代判断。API、运行时元数据、typed transport 与消费者
如果存在原子兼容关系，机械拆分可能更危险。

对 Ditto 的推断：按一个行为或一个不变量拆 PR，把无关清理移出；生成 diff 与手写 diff
分别评估。跨栈改动仍保留同提交身份与契约消费者，不能只为小 PR 打破发布原子性。

### 5. Google：优化响应速度和团队交付，而非个人产码速度

来源：[Speed of Code Reviews](https://google.github.io/eng-practices/review/reviewer/speed.html)。

Google 把一工作日视作审查响应的最长等待，通常让必要的多轮审查在一天内发生。
这里的重点是每次响应时间，不是保证所有变更一天合并。非关键剩余评论可以伴随
批准，审查也不应打断正在进行的深度工作。

边界：人类团队的响应目标不能直接证明 AI 项目应采取某个分钟数，更不能忽略上下文
载入与实质检查耗时。

对 Ditto 的推断：将“等待审查”“审查运行”“修改”“CI 排队/执行”分别计时。减少
不必要往返时延比降低标准更可取；同一结论应集中回复，轻微建议不触发整轮重新审查。

### 6. Google：审查范围与责任要说清楚

来源：[What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html)。

指南要求检查设计、行为、复杂度、测试、命名、文档与规范，理解分配给自己的代码和
相关上下文。多个审查者可以分工，但应明确各自检查了哪些文件或方面。作者在送审时
应已测试到变更能正确运行，审查者仍需关注边界与并发。

边界：已有 CI 不替代语义审查；多个审查者也不自动构成全面覆盖。

对 Ditto 的推断：需求与规范两轴可以在同一固定 SHA 并行完成，但先合并去重结论。
由一名整合者裁定阻塞项，避免两个代理各自重启完整循环。第二轮检查修复及受影响
语义；当修复改变设计或不变量时扩大范围，其他部分保留已审覆盖记录。

### 7. DORA：小批量缩短反馈，但不能在下游重新聚成大批

来源：[Working in small batches](https://dora.dev/capabilities/working-in-small-batches/)。

DORA 将小批量视作快速验证假设和纠偏的能力。批次应尽量独立、有价值、可验证，
耗时以小时至数天计；开发拆小、测试或交付又重新汇总会抵消收益。当前页面特别提醒
AI 易快速生成大批代码，需要有意识地拆分与核验。

边界：组织研究的关联和能力模型不能推出个人仓库的因果收益百分比。Dark launch、
feature toggle 是示例，不是每个项目必须增建的架构。

对 Ditto 的推断：先减少单 PR 同时承担的独立行为与治理改动，不新建 feature flag
平台。依赖 PR 不必为了“并行”提前建立不稳定接口；优先让无依赖批次可先审先交付。

### 8. DORA：快速 CI 反馈层应在数分钟内给出结果

来源：[Continuous integration](https://dora.dev/capabilities/continuous-integration/)。

DORA 建议每个提交触发构建与快速可靠测试，数分钟内反馈；页面提出约 10 分钟上限，
超过时优化效率、并行或将慢测试拆入独立流水线。完整端到端测试依然必要。坏构建要
优先修复，交付包应可重复且由下游一致使用。

边界：约 10 分钟是快速反馈目标，不能解释成所有跨平台、容器、安全与发布证明必须
十分钟内完成，或超过十分钟的检查就可以不再阻塞。

对 Ditto 的推断：将最可能失败的静态、契约与受影响快速测试尽早暴露；慢层并行运行
或按真实依赖等待。用根 Task DAG 保持同一命令权威，先消除重复执行，再考虑更多算力。
最终适用门和精确提交、制品身份保留。

### 9. GitHub：过期批准与最新 push 批准是不同控制

来源：[About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)。

GitHub 可在 PR diff 或 merge base 变化时撤销批准；也支持只要求最近可审 push 得到
另一人的批准，以避免所有既有批准失效。官方说明后者是折衷，担心已批准 PR 被加入
未审内容时，撤销过期批准更安全。严格 up-to-date 状态检查会带来更多构建；宽松模式
减少重跑但增加合并后不兼容风险。

边界：这些是可选机制的取舍，不是推荐 Ditto 立即关闭保护。GitHub 身份批准与本地
AI 审查记录不是同一控制。

对 Ditto 的推断：先查当前真实规则，确认是否在 base 更新、小修订后重复触发批准及
构建。可以减少审查工作量而继续对最新 SHA 给出批准；保护配置更改需要单独明确授权。

### 10. GitHub：并发组能停止已经过时的 PR CI

来源：[Control workflow concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)。

同组默认最多一个运行和一个等待项，新等待项替换旧等待项；`cancel-in-progress`
可以取消旧运行。组名须包含 workflow 身份以避免跨 workflow 意外取消，PR 与发布等
场景可以使用不同策略。

边界：取消可恢复的过时验证与取消真实写入、上传或发布不是同一件事；需要检查作业
是否有持久副作用和清理职责。取消也不能用作新的 HEAD 已验证的证据。

对 Ditto 的推断：如果当前 PR 连续修复产生旧 SHA 作业，优先复用现有 concurrency。
不引入调度器；只对已确认无持久副作用的过时验证取消，保留最终 SHA 的完整适用门。

### 11. GitHub：缓存依赖与缓存验证结论不是同一件事

来源：[Dependency caching reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)。

GitHub 缓存按 key/restore-keys 匹配；已有缓存内容不可原位修改。PR 的缓存可受 merge
ref 范围限制。官方提醒缓存可能对 PR 作者可读，不能存 secrets，并注意不可信触发的
缓存写入与污染风险。

边界：缓存命中不证明 lockfile、工具链或代码验证通过；可恢复依赖可以宽匹配，验证
结论不能如此复用。

对 Ditto 的推断：测量 uv/Bun 下载、安装与缓存解压时间；key 按 OS、工具版本、lockfile
绑定，恢复后仍执行声明依赖与必要检查。不要缓存个人配置、数据库、token，也不要把
旧测试结果或安全扫描结论当作当前提交绿灯。

### 12. GitHub：同 SHA 的基础设施失败可重跑失败作业

来源：[Re-running workflows and jobs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)。

GitHub 支持全量、失败作业和指定作业重跑。重跑使用原事件的 `GITHUB_SHA`、`GITHUB_REF`
与原触发人的权限，不因按钮操作而转到最新代码。

边界：旧 run 重跑不能验证已修复的新 SHA；再次通过也不自动证明失败是 flaky。

对 Ditto 的推断：已确认网络或 runner 故障、代码未变时，使用失败作业重跑；逻辑或
配置改变则让新提交触发适用流水线。保存首个失败原因和后续结果，避免把重跑绿灯
抹成“从未失败”。

### 13. GitHub：AI 审查存在漏报、误报与错误修复

来源：[Application card: GitHub Copilot Agents](https://docs.github.com/en/copilot/responsible-use/agents)。

GitHub 明确说明 code review 会漏掉问题，会把不存在的问题误报为缺陷，建议的代码
可能语法或语义错误、无法解决发现，甚至带入安全问题。官方定位是辅助审查，并要求
审查和测试建议，而非无条件采纳。

边界：供应商声明证明风险存在，不给出 Ditto 或其他模型的误报比例。不能据此把不
喜欢的 AI 发现判成误报；也不能推断更多模型独立投票必然可靠。

对 Ditto 的推断：把 AI finding 当作待核验的缺陷主张。先追踪真实调用、信任边界与
反例；可复现则修复，无效则给出证据，不把“消灭评论”当目标。新增修复要检查它
是否扩大范围、改变资金/PIT/契约语义或产生新失败。

### 14. GitHub：自动 review 每次 push 是可配置触发

来源：[About GitHub Copilot code review](https://docs.github.com/en/copilot/concepts/agents/code-review)。

官方说明默认按请求审查，自动模式可对新 PR、draft 转 ready、每次 push 或 draft 启用。
若未配置每次 push，自动审查通常只有一次，后续可手动请求。不同配置共同影响触发；
PR 自定义指令还可能来自 head 分支。

边界：这是 Copilot 的机制，不能声称 Ditto 当前 CR 工具拥有同样的增量范围或执行行为。
当前产品设置会变化，采用前需要再次核对。

对 Ditto 的推断：如果实际工具设置为每个小提交全量重审，可先将一轮有效修复集中成
一次可审 push。审查指令本身改动时要明确本轮采用的版本；不为降频绕过最新提交审查。

## 如何把来源转成可归因的实验

以下均为研究建议，阈值是初始实验选择，不是外部行业定律。先对最近 10–20 个可比 PR
做一次人工标注，不创建长期观测平台。样本不足时报告样本，避免比例伪精确。

| 需要区分的问题 | 最少证据 | 判定信号 | 最小对应调整 |
|---|---|---|---|
| 实现首轮质量不足 | 固定首审 SHA、真实缺陷触发路径、对应测试 | 多个首次提交就存在的实质缺陷，且违反已确认需求 | 实现前端到端 trace、送审前复用现有验证；把最常见真实遗漏变成一条必要检查 |
| 首审不完整 | 相同首审 SHA 上后续发现的缺陷、审查覆盖记录 | 第二/三轮发现与修复无关、首轮已存在的实质缺陷 | 首轮按语义主流程完成覆盖；固定上下文与 scope，不追求先报小问题 |
| 修复引入回归 | 相邻两个 SHA 差异、首次出现失败 | 后续缺陷仅在修复差异中出现 | 集中修复相关根因，再验证受影响调用；复审增量与必要上下文 |
| 审核误报 | 发现主张、实际调用与反证 | 理解错误、不可能到达的前提、重复已闭合结论 | 一名整合者核验和关闭，记录理由；不修改正确行为来迎合 finding |
| 范围漂移/偏好阻塞 | 原 Issue、已确认决定、发现依据 | 新增非必要能力、未规定样式、等价方案争论 | 必须/可选分级，后续需求进入新 Issue；有依据的设计风险仍可阻塞 |
| CI 结构浪费 | job/step 时间、依赖 DAG、取消及重跑记录 | 等待明显超过计算；相同准备/测试重复；旧 SHA 占 runner | 先去重、并行无依赖作业、取消可恢复的旧验证、复用依赖缓存 |
| CI 不可靠 | 首失败日志、同 SHA 重跑、环境信息 | runner/网络故障、时间敏感测试或外部服务导致重复失败 | 修确定性根因；已确认基础设施故障只重跑失败作业，不把 retry 当修复 |

时间应按区间求并集，避免并行 CR 和 CI 重复加总。至少记录：ready-to-review 到首次
实质反馈、每次提交到首个可行动失败、每次提交到全部适用门结束、首审到可合并。
实现缺陷、首审遗漏、修复回归、误报、非阻塞建议、范围新增分别计数；评论数量不是
缺陷数量，review API 事件数量也不等于有效返工轮次。

试行 5 个可比 PR 时可提出：一轮完整审查、一次集中修复、一次修复复审为默认路径；
第三轮起必须说明新阻塞属于首审遗漏、修复回归、需求变化还是误报。它是归因触发点，
不是强制合并上限。快速 CI 首个可行动结果以 5–10 分钟为候选目标，同时看 p50/p90，
不承诺所有门达到该耗时。只有缺陷逃逸、关键不变量违规未增加，才认为实验改善有效。

优先不做：新审查平台、更多默认串行代理、全 PR 统一行数硬门、固定评分与零 finding
循环、取消实质正确性/安全/契约门、立刻迁移 runner 或新增生产依赖。现有 Task、GitHub
时间线和少量表格已足够检验第一轮假设。

## 与 Ditto 当前规范的关系

本次只读取当前[交付约定](../engineering/development-workflow.md)：它已经允许小任务
按风险直接验证，要求固定提交范围的需求/规范两轴审查，修复后检查新增差异，PR HEAD
与 CI SHA 一致，并由维护者合并。上述建议主要是明确如何判定有效发现、合并两轴结论
与度量等待，不能据此宣称当前规范强制无限复审或已部署某个审查机器人。

真实执行流程是否比文档更重、作业耗时是否由 runner/容器/外部扫描主导、当前保护与
自动 review 配置如何，必须由本轮 Ditto 审计补证。本文没有修改任何配置、批准、门禁
或 GitHub 状态。
