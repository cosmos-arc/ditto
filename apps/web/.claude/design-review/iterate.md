# 自主迭代模式

> **无需人工介入**，自动循环创意方向→审查→修复→评分→反思，直到达标或达到上限。
> **创意流程借鉴**：CREATIVE DIRECTION 从 [CREA 框架](https://crea-diffusion.github.io/)借鉴、REFLECT 从 [Reflexion 模式](https://arxiv.org/abs/2303.11366)借鉴、常态化标杆调研从 Design Harness 的 [Inspiration 层](https://agenticux.substack.com/p/between-uicrit-and-autoresearch-what)借鉴。

---

## 参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `--iterate` | off | 启用自主迭代模式 |
| `--goal` | 8.0 | 综合气质分目标 |
| `--max-rounds` | 3 | 最大迭代轮次 |

> **三区架构适配**: 原型采用三区 Hash 导航（default-view / states-gallery / overlays-gallery）。
> State Coverage 检查不再依赖 `<details>` 展开检测，改为检查 `states-gallery` 中 `.gallery-card` 的数量和 label 是否匹配 State Coverage Index。
> REFLECT 阶段评估状态覆盖时，以 gallery card 覆盖率而非 `<details>` 展开数为依据。
>
> **批量操作安全规则**: 涉及 HTML 原型的批量操作（迁移/重构/审计），必须用 DOM 解析器（如 BeautifulSoup），禁止使用正则表达式。禁止用字符串拼接/正则做结构性变更。audit 必须验证元素在正确的父容器内（用 CSS 选择器或不能只检查数量。
> 根因事故: 正则把 `<input>` 转义为 `&lt;input&gt;`，overlay-backdrop 被包进 `display: none` 的 section 内。
>
> **批量迁移完整性规则**: 涉及三区架构迁移（从 `<details>` 到 gallery-card），迁移前必须：
> 1. 统计迁移前 `<details class="state-variant">` 总数（N_before）
> 2. 迁移后统计 `states-gallery .gallery-card` 总数（N_after）
> 3. N_after >= N_before，否则阻断并报告缺失的变体
> 4. 同理对 overlay：迁移前 `.overlay-backdrop` 总数 vs 迁移后 `overlays-gallery .gallery-card` 总数
> 5. 每页迁移后立即验证 section 平衡（open == close），不等全部完成
> 根因事故: 16fe443 批量迁移 16 页面时，4 页面 state-variant 被删除但未迁移到 gallery（93 个状态变体丢失），3 页面 section 未关闭。

## 循环架构

```
VERSION [sonnet] → BASELINE [sonnet]
  │
  ├─ Loop (round 1..max-rounds)
  │   │
  │   ├─ Phase 2: CREATIVE DIRECTION  [opus]（创意蓝图：策略选择 + 轻量标杆调研）
  │   ├─ Phase 3: PARALLEL REVIEW     [按角色分配]
  │   ├─ Phase 4: CONFLICT RESOLUTION  [opus]
  │   ├─ Phase 5: AUTO-DECISION        [sonnet]（自动裁决，不阻塞用户）
  │   ├─ Phase 6: FIX                  [sonnet]
  │   ├─ Phase 7: POLISH               [混合: AD=opus, skills=sonnet]
  │   ├─ SCORE: 评分快照               [opus]
  │   ├─ REFLECT: 反思记录             [opus]
  │   │
  │   ├─ 达标？ ──是──→ 退出循环
  │   │
  │   └─ 无进展？ ──是──→ 瓶颈诊断 → 策略转向（详见「突破机制」）
  │
  └─ Phase 8: FINAL [混合] → Phase 9: SYNC [sonnet]
```

## 退出条件

**达标退出（全部满足）：**
- 综合气质分 ≥ goal
- P0 = 0（含视口截断 P0）
- 所有视觉指纹指标在阈值内
- VP-STANDARD (1536x1080) 内容完整性通过
- VP-COMPACT (1366x768) 内容完整性通过

**提前退出（任一满足）：**
- 连续 2 轮综合分变化 < 0.2 且**突破机制也未能产生有效方案**
- 已达到 max-rounds
- 反思记录连续 2 轮标记"无新方向可探索"

## Phase 2: CREATIVE DIRECTION（创意蓝图）

> **从 [CREA 框架](https://crea-diffusion.github.io/) 借鉴**：每轮迭代前，Art Director 定义本轮创意方向。
> 不是被动等审查发现问题，而是主动决定"这轮要往哪个方向优化"。

### 步骤

1. **回顾历史**：读取前轮评分快照和反思记录（首轮无历史则跳过）
2. **瓶颈识别**：识别当前最低分维度和已达天花板的维度
3. **创意策略选择**：从策略矩阵中选择本轮方向

| 优先级 | 策略 | 触发条件 | 业界参考 |
|--------|------|---------|---------|
| 1 | 基础修补 | P0 > 0 或有基础缺陷（≤ 7.0） | — |
| 2 | 定向精修 | 特定维度 < 8.0，需定向提升 | 标杆产品对应维度 |
| 3 | 一致性打磨 | 各维度 ≥ 8.0 但一致性 < 8.5 | Linear, Vercel |
| 4 | 创意突破 | 连续 2 轮无进展，或某维度达天花板 | Bloomberg, TradingView |
| 5 | 整体气质提升 | 各维度 ≥ 9.0 但综合未达标 | 综合标杆 |

4. **轻量标杆调研**（每轮标配，非突破专属）：
- WebSearch 1-2 个标杆产品的具体实现
- 提取可落地的视觉手法（不需要深度调研，只需要 1-2 个具体参考点）
- 例："Bloomberg Terminal 信息密度布局"、"Linear 留白节奏设计"
- **不从 AutoResearch 借鉴的边界**：不做单变量实验，标杆参考用于**启发创意方向**而非逐项测试

5. **输出本轮创意蓝图**：

```
Round {N} 创意蓝图
├─ 策略: {从策略矩阵选择}
├─ 重点区域: {本轮聚焦优化的页面区域}
├─ 标杆参考: {1-2 个参考产品 + 具体参考点}
├─ 预期改进维度: {克制度/一致性/高级感/品牌方向/信息效率}
└─ 约束: {本轮不可触碰的方向（避免震荡）}
```

### 与突破机制的关系

CREATIVE DIRECTION 是**每轮标配**的前置规划，突破机制是**特殊触发**的深度转向。两者共享策略矩阵但执行深度不同：

| 维度 | CREATIVE DIRECTION（每轮） | 突破机制（触发时） |
|------|---------------------------|-------------------|
| 标杆调研 | 1-2 个轻量参考 | 深度调研 + 多参考对比 |
| 策略选择 | 从 5 级优先级选择 | 从转向矩阵选择（更激进） |
| 产出 | 一段创意蓝图 | 完整突破方案 + 变更清单 |

## 突破机制（Breakthrough Protocol）

> **核心洞察**: 当连续多轮优化收益递减时，问题往往不在"做得不够好"，而在**优化维度本身已耗尽**。
> 此时需要**换一个维度思考**，而非在同一维度上继续打磨。

### 触发条件

当 SCORE 阶段检测到以下任一情况时，自动触发突破机制：

```
触发条件（任一）：
├─ 连续 2 轮综合分变化 < 0.2（原 diminishing returns 阈值）
├─ 某维度连续 3 轮无变化（该维度已达局部最优）
└─ 综合分距离 goal ≥ 0.3 且已消耗 >60% 的 max-rounds
```

### 第一步：瓶颈诊断（Bottleneck Diagnosis）

在触发突破前，先诊断分数卡在哪、为什么卡住：

```
瓶颈诊断模板：
├─ 1. 分析评分快照：哪个维度拖后腿？
│     ├─ 克制度瓶颈 → 所有 AD 阈值已达标，无法继续"减"
│     ├─ 一致性瓶颈 → Token/字体/间距已统一，无更多"对齐"空间
│     ├─ 高级感瓶颈 → 视觉品质已精修，缺乏"记忆点"和"sophistication"
│     └─ 品牌方向瓶颈 → DNA 元素已覆盖，缺乏"signature moment"
│
├─ 2. 分析优化历史：最近 N 轮做了什么类型的变更？
│     ├─ 全是"减法"（减少字号/装饰/颜色）→ 减法天花板已到
│     ├─ 全是"对齐"（统一 Token/间距/字体）→ 一致性已饱和
│     └─ 全是"修补"（修 P0/修对比度/修截断）→ 基础问题已清零
│
└─ 3. 识别"空白维度"：哪些评分维度从未被主动优化过？
      └─ 瓶颈往往在"没人碰过"的维度里
```

### 第二步：策略转向矩阵

根据瓶颈诊断结果，选择对应的转向策略：

| 当前优化模式 | 已耗尽信号 | 转向策略 | 业界参考 |
|-------------|-----------|---------|---------|
| **减法优化**（减字号/减装饰/减颜色） | AD 阈值全部达标，分数不再上升 | → **信息可视化加法**：热力图、sparkline、数据着色、条件格式 | Bloomberg Terminal, TradingView |
| **对齐优化**（统一 Token/间距/字体） | 字号/ls/density 已标准化 | → **材质感加法**：noise texture、backdrop blur、glass morphism、elevation 层次 | Linear, Vercel, Raycast |
| **修补优化**（修 P0/对比度/截断） | P0 = 0，Lighthouse ≥ 90 | → **交互品质加法**：micro-animation、focus ring、hover glow、keyboard affordance | Arc Browser, Notion |
| **装饰优化**（加 badge/加 glow/加动画） | 克制度分数下降或 AD 否决 | → **数据密度优化**：信息架构重组、progressive disclosure、数据分层 | Bloomberg, Stripe Dashboard |
| **单向优化**（只改 CSS） | CSS-only 改动收益递减 | → **结构优化**：HTML 语义增强、SVG 图形、Web Component、数据属性驱动 | — |

### 第三步：标杆调研（Benchmark Research）

选定转向策略后，用 WebSearch 调研标杆产品的具体实现：

```
调研流程：
1. WebSearch: "{标杆产品} {关键特性} design implementation"
   例: "Bloomberg Terminal heat map grid design"
   例: "Linear app backdrop blur glass effect CSS"

2. 分析标杆的核心手法：
   ├─ 它用什么技术手段实现这个效果？（CSS/SVG/Canvas/WebGL）
   ├─ 这个效果为什么让人觉得"高级"？（信息密度？材质感？动态反馈？）
   ├─ 能否在当前克制框架内复现？（不违反 AD 阈值）

3. 提取可落地的变更清单：
   ├─ 每个变更标注「影响维度」和「预期提分」
   ├─ 按影响力排序
   └─ 评估与现有 AD 阈值的兼容性
```

### 第四步：突破执行

```
突破执行原则：
├─ 1. 按影响力排序，CSS-only 优先（风险最低）
├─ 2. 每个"加法"变更必须回答：这是装饰还是信息？
│     ├─ 信息型（数据可视化、材质感、交互反馈）→ 允许，不违反克制
│     └─ 装饰型（纯视觉花哨）→ AD 可否决
├─ 3. 每个变更不超过 0.05 opacity / 1px / 2px 的增量
│     → 极低增量确保"克制框架内"的一致性
└─ 4. 执行后必须重新跑全部 AD 阈值检测
      → 确保突破没有侵蚀已建立的基础
```

### 第五步：突破评分

突破变更执行后，SCORE 阶段增加突破专项评估：

```
突破评分（附加到评分快照）：
├─ 突破轮次标记: ★（区分于常规迭代轮次）
├─ 转向策略: 减法→加法（信息可视化）
├─ 新增维度覆盖: heat map ✓, sparkline ✓, noise texture ✓
├─ AD 阈值回归检测: 全部通过 ✓
└─ 突破增量: +0.25（vs 前轮 +0.0）
```

### 突破失败处理

如果突破机制执行后仍无进展（分数变化 < 0.1）：

```
突破失败处理：
├─ 1. 记录失败原因（哪个策略无效、为什么）
├─ 2. 尝试下一个转向策略（从策略矩阵中选择）
├─ 3. 如果所有策略都尝试过仍无进展 → 诚实报告天花板
│     └─ 输出「天花板分析报告」：当前分数、瓶颈根因、
│        建议的后续方向（如 React 实现阶段才能突破的限制）
└─ 4. 不伪造分数，不虚报进展
```

## AUTO-DECISION 规则（替代人工 Phase 5）

自主模式下，Phase 5 不阻塞用户，按以下优先级自动决策：

```
优先级 0: C 类产品边界门控 → PM 深度分析流程
    │
    ├─ Step 1: PM 分歧评估
    │   ├─ 量化分歧程度：低 / 中 / 高
    │   ├─ 识别分歧类型：spec 缺失 / 功能增删 / 方向性选择 / 优先级冲突
    │   └─ 记录各角色立场和理由
    │
    ├─ Step 2: 业界调研（WebSearch 2-3 个标杆）
    │   ├─ 搜索同类产品如何处理该场景
    │   ├─ 提取可参考的设计决策和理由
    │   └─ 评估调研结果对本项目的适用性
    │
    ├─ Step 3: 调研裁决
    │   ├─ 调研能明确解决分歧 → PM 自动裁决
    │   │   ├─ 记录：裁决结果 + 调研依据 + 标杆参考
    │   │   └─ 进入正常修复流程
    │   └─ 调研无法明确解决 → 进入 Step 4
    │
    └─ Step 4: 分歧等级裁决
        │
        ├─ 低分歧（单角色提出，spec 有间接参考）
        │   └─ PM 直接裁决，记录分析依据
        │
        ├─ 中分歧（2 角色有分歧，不涉及核心场景）
        │   └─ PM 分析权衡后裁决，记录分歧分析 + 裁决理由
        │
        └─ 高分歧（满足任一条件）：
            ├─ 条件 A: 多角色对立 + spec 缺失
            ├─ 条件 B: PM 自身无法判断（信息不足或重大业务权衡）
            └─ 条件 C: 方向性产品选择（影响产品定位或核心用户场景）
            → 先执行 PM 推荐方案（标记「待确认」）
            → ESCALATE 给用户，附带结构化分析（见 ESCALATE 模板）
            → 用户后续可通过 git diff 查看变更或回滚

    ※ 分歧记录纳入当轮反思（REFLECT），供后续轮次参考
优先级 1: P0 全部采纳 → 无条件修复
优先级 2: 共识点全部采纳 → 所有一致认同的建议直接执行
优先级 3: 冲突点 → 按双轨权威制自动裁决：
    ├─ 视觉决策轨（AD 最高）：
    │   ├─ AD vs UI（装饰 vs Token）→ AD 胜
    │   ├─ AD vs UX（affordance vs 高级感）→ UX 胜（可访问性不妥协）
    │   └─ AD vs 所有（整体气质 vs 局部优化）→ AD 整体视角胜
    ├─ 产品决策轨（PM 最高）：
    │   ├─ PM vs AD（产品内容 vs 视觉表达）→ PM 定内容边界
    │   ├─ PM vs IA（功能范围 vs 信息结构）→ PM 定范围
    │   └─ PM vs UX（功能完整 vs 交互简化）→ PM 裁定功能必要性
    └─ 信息架构决策轨（IA 最高）：
        └─ IA vs UX（信息分组 vs 交互路径）→ IA 定结构
优先级 4: P1 选择性采纳 → 按评分缺口定向选取：
    ├─ Art Director 在 CONFLICT 阶段为每个 P1 标注「预期提分」
    ├─ 按预期提分从高到低排序
    └─ 选取直到预计总分能达标（留 0.3 安全余量）
优先级 5: P2 → 仅在后续轮次且仍有缺口时才考虑
优先级 6: 突破变更 → 触发突破机制时，按「突破执行」原则实施
优先级 7: 创意蓝图对齐 → AUTO-DECISION 采纳的变更需与 CREATIVE DIRECTION 蓝图方向一致：
    ├─ 与蓝图方向一致的变更 → 优先采纳
    ├─ 与蓝图方向无关但确实解决 P0/P1 的变更 → 正常采纳，但在反思中标记为"非蓝图变更"
    └─ 蓝图不得含 C 类变更（CREATIVE DIRECTION 阶段应已排除，此处为最后防线）
```

### 分歧等级定义

| 等级 | 触发条件 | 裁决方式 | 记录要求 |
|------|---------|---------|---------|
| **低** | 单角色提出，spec 有间接参考，不影响核心场景 | PM 直接裁决 | 一句话理由 |
| **中** | 2 角色有分歧，或 spec 模糊但可推断，不涉及核心场景 | PM 分析权衡后裁决 | 分歧分析 + 裁决理由 |
| **高** | 满足任一：多角色对立+spec缺失 / PM无法判断 / 方向性选择 | PM 推荐 + ESCALATE | 结构化 ESCALATE 分析 |

### PM 裁决范围

| 变更类型 | PM 权限 | 说明 |
|---------|---------|------|
| spec 内优先级调整 | ✅ 自动裁决 | P0/P1/P2 权重重排 |
| spec 内布局调整 | ✅ 自动裁决 | 模块位置、排列方式 |
| spec 内交互方式调整 | ✅ 自动裁决 | 点击 vs hover vs drag 等 |
| 弱化 spec 低优先级功能 | ⚠️ 需分析 | PM 评估影响后裁决，记录理由 |
| 新增 spec 未定义内容 | ⚠️ 需调研+分析 | 走完整 Step 1-4 |
| 删除 spec 高优先级功能 | ⚠️ 需调研+分析 | 走完整 Step 1-4 |
| 方向性产品选择 | 🔴 ESCALATE | 影响产品定位或核心场景 |

## 防震荡机制

- 每轮记录「已采纳决策集」
- 后续轮次**不推翻**已采纳的决策（除非新问题导致必须回退）
- 连续 2 轮总分变化 < 0.2 → **不立即退出**，触发突破机制
- 突破机制执行后仍无进展 → 退出并报告天花板
- 每轮 CREATIVE DIRECTION 必须读取前轮的创意蓝图和反思记录
- 创意策略不得与前 2 轮重复（除非基础修补策略仍有 P0）
- 标杆参考不得与前一轮完全相同

## 基线修正规则（Baseline Correction）

> **核心原则**: 当前轮的评分只衡量当前轮的改动，不应因"发现上一轮的遗漏"而扣当前轮的分。

当 SCORE 阶段发现前序轮次遗漏的问题时：

```
处理方式：
├─ 1. 问题记录为 P2/P3 backlog，标注发现轮次和来源轮次
├─ 2. 修正前序轮次的基线分（追溯调整）
│     └─ 例: R10 声称 9.88，R11 发现 R10 遗漏 14px → R10 真实基线 9.86
├─ 3. 当前轮的 delta 仅基于当前轮的改动计算
│     └─ 例: R11 改动贡献 +0.06 克制度 +0.05 高级感 → R11 delta = 正向
└─ 4. 综合气质 = 修正后的前序基线 + 当前轮 delta
      └─ 例: 9.86 + 0.02 = 9.88（而非 9.88 - 0.06 = 9.82）
```

**为什么重要**: 如果允许"发现旧问题扣当前轮分"，会导致分数与实际改动方向脱钩——
设计确实变好了，但数字反而下降，迭代失去可追踪性。

**判定标准**: 如果一个问题在当前轮之前就已存在（可通过 `git diff review/round-{N}` 验证），
则该问题属于前序轮次遗漏，不应影响当前轮评分。

## 每轮反思记录（REFLECT）

> **从 [Reflexion 模式](https://arxiv.org/abs/2303.11366) 借鉴**：维护跨轮次的定性记忆，
> 记录"为什么有效/无效"，避免重复无效方向。设计效果是整体性的，
> 反思记录关注的是**创意方向的成败**，而非逐个变更的成败。

每轮 SCORE 之后，Art Director 输出结构化反思：

```
Round {N} 反思：
├─ 本轮创意策略: [策略名 + 方向]
├─ 实际执行: [变更摘要，2-3 句]
├─ 效果:
│   ├─ 分数变化: {各维度变化}
│   └─ 整体感受: [有效/无效/中性] + [一句话原因]
├─ 关键洞察:
│   ├─ 什么起了作用: [具体手法 + 为什么]
│   └─ 什么没起作用: [具体手法 + 为什么]
├─ 死胡同标记: [明确无效的方向，下轮应避免]
└─ 可探索方向: [有潜力但本轮未充分尝试的方向]
```

**反思记录的用途**：
- 下轮 CREATIVE DIRECTION 阶段的**必读输入**
- 突破机制瓶颈诊断的**定性数据**（不只是看分数趋势）
- 最终报告迭代历程的**定性补充**
