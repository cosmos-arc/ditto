# 自主迭代模式

> **无需人工介入**，自动循环审查-修复-评分，直到达标或达到上限。

---

## 参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `--iterate` | off | 启用自主迭代模式 |
| `--goal` | 8.0 | 综合气质分目标 |
| `--max-rounds` | 3 | 最大迭代轮次 |

---

## 循环架构

```
VERSION [sonnet] → BASELINE [sonnet]
  │
  ├─ Loop (round 1..max-rounds)
  │   │
  │   ├─ Phase 2: PARALLEL REVIEW    [按角色分配]
  │   ├─ Phase 3: CONFLICT RESOLUTION [opus]
  │   ├─ Phase 4: AUTO-DECISION       [sonnet]（自动裁决，不阻塞用户）
  │   ├─ Phase 5: FIX                 [sonnet]
  │   ├─ Phase 6: POLISH              [混合: AD=opus, skills=sonnet]
  │   ├─ SCORE: 评分快照              [opus]
  │   │
  │   ├─ 达标？ ──是──→ 退出循环
  │   │
  │   └─ 无进展？ ──是──→ 瓶颈诊断 → 策略转向（详见「突破机制」）
  │
  └─ Phase 7: FINAL [混合] → Phase 8: SYNC [sonnet]
```

---

## 退出条件

**达标退出（全部满足）：**
- 综合气质分 ≥ goal
- P0 = 0（含视口截断 P0）
- 所有视觉指纹指标在阈值内
- VP-STANDARD (1536x1080) 内容完整性通过
- VP-COMPACT (1366x768) 内容完整性通过

**提前退出（任一满足）：**
- 连续 2 轮综合分变化 < 0.2 且**突破机制也未能产生有效方案**
- 已达到 max-rounds

---

## 突破机制（Breakthrough Protocol）

> **核心洞察**: 当连续多轮优化收益递减时，问题往往不在"做得不够好"，而在**优化维度本身已耗尽**。
> 此时需要**换一个维度思考**，而非在同一维度上继续打磨。

### 触发条件

当 SCORE 阶段检测到以下任一情况时，自动触发突破机制：

```
触发条件（任一）：
├─ 连续 2 轮综合分变化 < 0.2（原 diminishing returns 阈值）
├─ 某维度连续 3 轮无变化（该维度已达局部最优）
└─ 综合分距离 goal ≥ 0.3 且已消耗 >60% 的 max-rounds
```

### 第一步：瓶颈诊断（Bottleneck Diagnosis）

在触发突破前，先诊断分数卡在哪、为什么卡住：

```
瓶颈诊断模板：
├─ 1. 分析评分快照：哪个维度拖后腿？
│     ├─ 克制度瓶颈 → 所有 AD 阈值已达标，无法继续"减"
│     ├─ 一致性瓶颈 → Token/字体/间距已统一，无更多"对齐"空间
│     ├─ 高级感瓶颈 → 视觉品质已精修，缺乏"记忆点"和"sophistication"
│     └─ 品牌方向瓶颈 → DNA 元素已覆盖，缺乏"signature moment"
│
├─ 2. 分析优化历史：最近 N 轮做了什么类型的变更？
│     ├─ 全是"减法"（减少字号/装饰/颜色）→ 减法天花板已到
│     ├─ 全是"对齐"（统一 Token/间距/字体）→ 一致性已饱和
│     └─ 全是"修补"（修 P0/修对比度/修截断）→ 基础问题已清零
│
└─ 3. 识别"空白维度"：哪些评分维度从未被主动优化过？
      └─ 瓶颈往往在"没人碰过"的维度里
```

### 第二步：策略转向矩阵

根据瓶颈诊断结果，选择对应的转向策略：

| 当前优化模式 | 已耗尽信号 | 转向策略 | 业界参考 |
|-------------|-----------|---------|---------|
| **减法优化**（减字号/减装饰/减颜色） | AD 阈值全部达标，分数不再上升 | → **信息可视化加法**：热力图、sparkline、数据着色、条件格式 | Bloomberg Terminal, TradingView |
| **对齐优化**（统一 Token/间距/字体） | 字号/ls/density 已标准化 | → **材质感加法**：noise texture、backdrop blur、glass morphism、elevation 层次 | Linear, Vercel, Raycast |
| **修补优化**（修 P0/对比度/截断） | P0 = 0，Lighthouse ≥ 90 | → **交互品质加法**：micro-animation、focus ring、hover glow、keyboard affordance | Arc Browser, Notion |
| **装饰优化**（加 badge/加 glow/加动画） | 克制度分数下降或 AD 否决 | → **数据密度优化**：信息架构重组、progressive disclosure、数据分层 | Bloomberg, Stripe Dashboard |
| **单向优化**（只改 CSS） | CSS-only 改动收益递减 | → **结构优化**：HTML 语义增强、SVG 图形、Web Component、数据属性驱动 | — |

### 第三步：标杆调研（Benchmark Research）

选定转向策略后，用 WebSearch 调研标杆产品的具体实现：

```
调研流程：
1. WebSearch: "{标杆产品} {关键特性} design implementation"
   例: "Bloomberg Terminal heat map grid design"
   例: "Linear app backdrop blur glass effect CSS"

2. 分析标杆的核心手法：
   ├─ 它用什么技术手段实现这个效果？（CSS/SVG/Canvas/WebGL）
   ├─ 这个效果为什么让人觉得"高级"？（信息密度？材质感？动态反馈？）
   ├─ 能否在当前克制框架内复现？（不违反 AD 阈值）

3. 提取可落地的变更清单：
   ├─ 每个变更标注「影响维度」和「预期提分」
   ├─ 按影响力排序
   └─ 评估与现有 AD 阈值的兼容性
```

### 第四步：突破执行

```
突破执行原则：
├─ 1. 按影响力排序，CSS-only 优先（风险最低）
├─ 2. 每个"加法"变更必须回答：这是装饰还是信息？
│     ├─ 信息型（数据可视化、材质感、交互反馈）→ 允许，不违反克制
│     └─ 装饰型（纯视觉花哨）→ AD 可否决
├─ 3. 每个变更不超过 0.05 opacity / 1px / 2px 的增量
│     → 极低增量确保"克制框架内"的一致性
└─ 4. 执行后必须重新跑全部 AD 阈值检测
      → 确保突破没有侵蚀已建立的基础
```

### 第五步：突破评分

突破变更执行后，SCORE 阶段增加突破专项评估：

```
突破评分（附加到评分快照）：
├─ 突破轮次标记: ★（区分于常规迭代轮次）
├─ 转向策略: 减法→加法（信息可视化）
├─ 新增维度覆盖: heat map ✓, sparkline ✓, noise texture ✓
├─ AD 阈值回归检测: 全部通过 ✓
└─ 突破增量: +0.25（vs 前轮 +0.0）
```

### 突破失败处理

如果突破机制执行后仍无进展（分数变化 < 0.1）：

```
突破失败处理：
├─ 1. 记录失败原因（哪个策略无效、为什么）
├─ 2. 尝试下一个转向策略（从策略矩阵中选择）
├─ 3. 如果所有策略都尝试过仍无进展 → 诚实报告天花板
│     └─ 输出「天花板分析报告」：当前分数、瓶颈根因、
│        建议的后续方向（如 React 实现阶段才能突破的限制）
└─ 4. 不伪造分数，不虚报进展
```

## AUTO-DECISION 规则（替代人工 Phase 4）

自主模式下，Phase 4 不阻塞用户，按以下优先级自动决策：

```
优先级 1: P0 全部采纳 → 无条件修复
优先级 2: 共识点全部采纳 → 所有一致认同的建议直接执行
优先级 3: 冲突点 → 按 AD 优先级规则自动裁决：
    ├─ AD vs UI（装饰 vs Token）→ AD 胜
    ├─ AD vs PM（功能标签 vs 克制）→ AD 可要求更安静实现
    ├─ AD vs UX（affordance vs 高级感）→ UX 胜（可访问性不妥协）
    └─ AD vs 所有（整体气质 vs 局部优化）→ AD 整体视角胜
优先级 4: P1 选择性采纳 → 按评分缺口定向选取：
    ├─ Art Director 在 CONFLICT 阶段为每个 P1 标注「预期提分」
    ├─ 按预期提分从高到低排序
    └─ 选取直到预计总分能达标（留 0.3 安全余量）
优先级 5: P2 → 仅在后续轮次且仍有缺口时才考虑
优先级 6: 突破变更 → 触发突破机制时，按「突破执行」原则实施
```

## 防震荡机制

- 每轮记录「已采纳决策集」
- 后续轮次**不推翻**已采纳的决策（除非新问题导致必须回退）
- 连续 2 轮总分变化 < 0.2 → **不立即退出**，触发突破机制
- 突破机制执行后仍无进展 → 退出并报告天花板

## 基线修正规则（Baseline Correction）

> **核心原则**: 当前轮的评分只衡量当前轮的改动，不应因"发现上一轮的遗漏"而扣当前轮的分。

当 SCORE 阶段发现前序轮次遗漏的问题时：

```
处理方式：
├─ 1. 问题记录为 P2/P3 backlog，标注发现轮次和来源轮次
├─ 2. 修正前序轮次的基线分（追溯调整）
│     └─ 例: R10 声称 9.88，R11 发现 R10 遗漏 14px → R10 真实基线 9.86
├─ 3. 当前轮的 delta 仅基于当前轮的改动计算
│     └─ 例: R11 改动贡献 +0.06 克制度 +0.05 高级感 → R11 delta = 正向
└─ 4. 综合气质 = 修正后的前序基线 + 当前轮 delta
      └─ 例: 9.86 + 0.02 = 9.88（而非 9.88 - 0.06 = 9.82）
```

**为什么重要**: 如果允许"发现旧问题扣当前轮分"，会导致分数与实际改动方向脱钩——
设计确实变好了，但数字反而下降，迭代失去可追踪性。

**判定标准**: 如果一个问题在当前轮之前就已存在（可通过 `git diff review/round-{N}` 验证），
则该问题属于前序轮次遗漏，不应影响当前轮评分。
