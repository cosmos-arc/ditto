# 审查角色定义

> 六角色并行审查的完整定义、审查清单和工具分配。

---

## UI Designer（视觉设计审查）

**关注维度：** 视觉品质、Token 一致性、布局节奏、色彩运用、字体排版

**审查清单：**

| 检查项 | 说明 |
|--------|------|
| Design Token 一致性 | 颜色/间距/字号是否使用 CSS 变量，是否有硬编码值 |
| 视觉层次 | 标题/正文/辅助文本的层次是否清晰 |
| 色彩运用 | 主色/强调色/功能色使用是否恰当，对比度是否足够 |
| 字体排版 | 字号/字重/行高的节奏是否和谐；是否遵循 body/heading/data/code 4-role 分工；数据组件是否启用 `tabular-nums slashed-zero`；代码组件是否 `ligatures: none` |
| 字体 Token 一致性 | `font-family-*` 是否按角色正确分配（heading 仅限气质层，data 仅限数字精度层，body 覆盖底座）；line-height 是否使用 token 而非硬编码 |
| 间距节奏 | 组件间/内容间的间距是否一致且合理 |
| 布局平衡 | 对齐方式、留白比例、视觉重心 |
| 响应式 | 不同断点下的布局表现 |
| 风格一致性 | 与其他页面的视觉风格是否统一 |
| 跨页组件尺寸一致性 | 与 manifest 中其他 done 页面的组件 metrics（table header / card padding / badge / button）对比，标记偏离值 |

**使用工具：**
- Chrome DevTools MCP: `take_screenshot` + `evaluate_script` 提取 computed styles
- 对比 token 定义：`tokens-style.css` / `tokens-base.css`
- impeccable skills: `normalize`, `colorize`, `typeset`, `arrange`

## UX Reviewer（交互体验审查）

**关注维度：** 可用性、可访问性、交互流程、信息架构、响应式体验

**审查清单：**

| 检查项 | 说明 |
|--------|------|
| 信息架构 | 内容组织是否合理，用户能否快速找到目标 |
| 交互流程 | 核心用户路径是否顺畅，有无断裂点 |
| 可访问性 | WCAG 合规（颜色对比度、键盘导航、aria 标签） |
| 视口完整性 | VP-STANDARD (1536x1080) 下所有内容可见，无截断（详见 [viewport.md](viewport.md)） |
| 反馈机制 | 操作反馈是否及时明确（loading、success、error） |
| 错误处理 | 错误状态是否有清晰提示和恢复路径 |
| 空状态 | 列表/数据为空时的展示是否友好 |
| 响应式交互 | 移动端触摸目标大小、手势交互 |
| 跨页交互模式一致性 | 同类型页面（如表格页 vs 表格页）的交互模式（hover、sort、filter）是否一致 |
| 认知负荷 | 单屏信息量是否适中，是否需要渐进展示 |

#### 产品适配检查（参考 [00_ditto_product_criteria.md](../../docs/designs/specs/00_ditto_product_criteria.md)）

| 检查项 | 量化方法 | 阈值 | 优先级 |
|--------|---------|------|--------|
| 交互元素最小尺寸 | tab/button/link 的 computed height | ≥ 24px | **P0** |
| Fixed 元素遮挡 | fixed/sticky 元素与内容的重叠高度 | 0px | **P0** |
| 10px 使用审计 | 10px 元素是否仅用于纯辅助信息（非交互/非导航） | 0 违规 | P1 |
| 小字号对比度 | 所有 ≤10px 元素的 oklch L 值 | L ≥ 0.60 | P1 |
| 间距梯度合理性 | 模块间间距是否按信息层级递减 | 符合梯度准则 | P1 |

**使用工具：**
- Chrome DevTools MCP: 交互测试、tab 导航、`lighthouse_audit`
- impeccable skills: `critique`, `audit`, `harden`

## Product Manager（产品功能审查）

**关注维度：** 功能完整性、用户场景覆盖、数据展示、业务规则正确性

> **边界**: PM 关注「功能有无 + 数据对不对」，IA 关注「放哪 + 怎么找到」。两者互补，不重叠。

**审查清单：**

| 检查项 | 说明 |
|--------|------|
| 功能完整性 | spec 定义的功能是否全部实现 |
| 用户场景 | 关键用户场景是否覆盖（新增/查看/编辑/删除等） |
| 数据展示 | 数据格式/精度/单位是否合理 |
| 业务规则 | 涨跌色、排序逻辑、筛选条件等业务规则是否正确 |
| 状态管理 | 各种状态（加载/空/错误/边界）是否处理 |

**使用工具：**
- 对比 spec 文档：组件规范、交互状态规范
- ui-ux-pro-max skill

## Copy Editor（界面语言审查）

**关注维度：** 文案清晰度、语气一致性、标签准确性、中文表达质量

**审查清单：**

| 检查项 | 说明 |
|--------|------|
| 标签准确性 | 按钮/菜单/字段的标签是否准确描述功能 |
| 文案清晰度 | 用户能否理解每段文案的含义 |
| 语气一致性 | 整体语气是否统一（专业但不冷漠） |
| 中英文混排 | 混排规则是否一致（间距、标点） |
| 数字/单位 | 格式是否统一（百分比/小数/千分位） |
| 空间效率 | 文案是否简洁，不浪费屏幕空间 |

**使用工具：**
- impeccable skills: `clarify`

## Data Viz Specialist（数据可视化审查）

**关注维度：** 数据表达准确性、图表 Token 使用、色觉无障碍、信息密度合理性

**审查清单：**

| 检查项 | 说明 |
|--------|------|
| 数据新鲜度反馈 | 实时数据是否有老化/衰减的视觉表达 |
| 图表 Token 使用 | sparkline/图表是否使用 `--chart-*` / `--sparkline-*` token |
| 色觉无障碍 | 涨跌信息是否不仅依赖颜色（是否配合▲/▼符号） |
| 热力图/矩阵规范 | 条件格式是否使用 `--heatmap-*` scale |
| 资产类别色彩 | 跨市场组件是否使用 `--asset-*` 色彩体系 |
| 数据状态标识 | 连接/同步/断连状态是否通过 `--data-state-*` 表达 |
| Token 消费率 | 数据组件中 hardcoded 值是否收敛到 token |

**使用工具：**
- Chrome DevTools MCP: 色盲模拟、对比度检测
- impeccable skills: `audit`

## IA Specialist（信息架构审查）

**关注维度：** 信息架构、用户流程、页面蓝图、标签体系、边界情况

> **补齐 Garrett 五层模型中的 Structure + Scope 层。** PM 审「功能有无」，UX 审「交互是否顺畅」，IA 审「信息组织是否合理 + 用户能否到达目标」。三者形成链：PM 定义内容范围 → IA 组织结构 → UX 验证交互。

**审查清单：**

#### 信息架构

| 检查项 | 说明 | 优先级 |
|--------|------|--------|
| 内容分组逻辑 | 页面内的模块分组是否反映用户心智模型（而非技术架构） | P1 |
| 层级深度 | 信息层级是否 ≤ 3 层（用户不需要 3+ 次点击才能到达核心内容） | P1 |
| 导航可达性 | 从任何页面能否在 ≤ 3 步内到达目标信息 | P1 |
| 标签语义一致性 | 相同概念是否使用相同标签（跨页面一致性） | P1 |
| 中英术语对齐 | 中英文标签的映射是否一致，是否有混用/不统一 | P2 |

#### 用户流程

| 检查项 | 说明 | 优先级 |
|--------|------|--------|
| Happy path 完整性 | 核心任务从入口到完成的路径是否无断裂 | P0 |
| 入口设计 | 用户从外部进入页面的路径是否清晰 | P1 |
| 退出/返回路径 | 每个状态是否都有明确的返回或关闭操作 | P0 |
| 错误恢复 | 遇到错误后用户能否恢复到之前的状态 | P1 |
| 死端检测 | 是否存在没有出口的页面/状态 | P0 |
| 跨页数据流 | 页面间传递的数据（参数、状态）是否连续 | P1 |

#### 页面蓝图

| 检查项 | 说明 | 优先级 |
|--------|------|--------|
| 首屏信息优先级 | above fold 是否放置了最重要的信息 | P1 |
| 渐进展示 | 次要信息是否通过交互渐进展示（而非一次全部呈现） | P1 |
| 内容边界 | 页面是否承载了过多不相关的信息 | P2 |
| 信息时效分层 | 实时数据、周期数据、静态参考的分布是否合理 | P2 |

#### 边界情况

| 检查项 | 说明 | 优先级 |
|--------|------|--------|
| 长内容处理 | 长名称、长数字、长列表的溢出/截断方案 | P1 |
| 短内容处理 | 列表 1 项、空表格等极端情况 | P1 |
| 极端值处理 | 涨跌幅 999%、超大数字的展示 | P2 |
| 多视口信息完整性 | 窄视口下信息是否被合理隐藏而非截断 | P1 |

**使用工具：**
- 对比 spec 文档：信息架构、页面蓝图（[01_product_information_architecture.md](../../docs/designs/specs/01_product_information_architecture.md)、[02_core_page_blueprints.md](../../docs/designs/specs/02_core_page_blueprints.md)）
- Chrome DevTools MCP: 跨页导航验证、链接可达性检测
- impeccable skills: `critique`（信息架构层面的评价）

## Art Director（艺术总监审查）

**关注维度：** 高级感、克制度、跨页一致性、品牌方向锚定、信息效率

> **不只看气质，也看适配性。** 确保 Graphite Studio 的审美方向（Linear/Vercel/Raycast 的克制感 + Bloomberg/quant desk 的专业终端感）与产品功能定位协调。审查标准必须参考 [00_ditto_product_criteria.md](../../docs/designs/specs/00_ditto_product_criteria.md) 中的模块分层密度准则。

### 审查清单

#### 美学指标（原有）

| 检查项 | 量化方法 | 阈值/标准 |
|--------|---------|-----------|
| 高亮描边密度 | 统计页面中 `border`/`outline`/`box-shadow` 用作高亮的元素数量 | 单页 ≤ 5 处品牌色描边 |
| 强调色面积比 | `--brand-accent` 覆盖的视觉面积占总面积比例 | ≤ 3% |
| 视觉元素层级数 | 不同装饰元素类型数（badge/标签/状态点/编号/箭头/分隔线/图标） | ≤ 6 种 |
| 色彩种类数 | 页面中使用的不同语义色彩种类（不含 neutral） | ≤ 4 种功能色 |
| 跨页语言一致性 | 对比其他页面的视觉指纹差异度 | ≥ 7/10 |
| 跨页 metrics 偏离 | 与 Phase 1 跨页一致性基线的偏离项数（组件尺寸/排版/色彩） | 0 项偏离（新增偏离标记为 P1） |
| 品牌方向评分 | 整体气质偏向 Bloomberg/quant desk 还是 SaaS dashboard | ≥ 8/10 Bloomberg 方向 |

#### 产品适配指标（参考 [00_ditto_product_criteria.md](../../docs/designs/specs/00_ditto_product_criteria.md)）

| 检查项 | 量化方法 | 阈值/标准 |
|--------|---------|-----------|
| 留白节奏比 | 按模块分层评估（非全局一刀切） | L1 数据区 15-25%, L2 辅助区 25-35%, L3 装饰区 30-40% |
| 交互元素最小字号 | 所有 role="tab"/"button"/"link" 元素的 computed fontSize | ≥ 12px（10px 仅允许纯辅助信息） |
| 交互元素最小高度 | tab/button/link 的 computed height | ≥ 24px |
| 间距梯度 | 模块间间距是否按信息层级递减 | L1→L1: 24px, L1→L2: 16px, L2→L3: 12px |
| 信息密度 | chars/Kpx（L1 数据区） | ≥ 12 chars/Kpx |
| Fixed 元素遮挡 | fixed/sticky 元素与内容的重叠高度 | 0px（无遮挡） |

### 气质评分卡（6 维度）

```
气质评分卡：
├─ 克制度:    ████████░░ 8.2/10
├─ 一致性:    ███████░░░ 7.5/10
├─ 高级感:    ████████░░ 8.0/10
├─ 品牌方向:  ████████░░ 8.3/10
├─ 信息效率:  ████████░░ 7.8/10   ← 产品适配
├─ 数据表达:  ███████░░░ 7.2/10   ← 量化平台专用
└─ 综合气质:  ████████░░ 7.8/10   (6 维均值)
```

**信息效率评分细则**:
- 信息密度 (chars/Kpx ≥ 12): +2.5
- 交互元素适配 (字号 ≥ 12px, 高度 ≥ 24px): +2.5
- 模块分层密度 (L1/L2/L3 各自符合准则): +2.5
- 间距梯度 (按层级递减，无固定大间距): +2.5

**数据表达评分细则**:
- 数据新鲜度反馈 (老化衰减可视化): +2.5
- 色觉无障碍 (涨跌色 + 形状辅助): +2.5
- Token 消费率 (数据组件 var() ≥ 80%): +2.5
- 可视化 Token 使用 (图表/热力图用 token): +2.5

### 评分瓶颈分析指南

> **每次评分时，除了打分，还必须标注每个维度的瓶颈类型。** 这是突破机制的诊断输入。

| 分数区间 | 瓶颈类型 | 含义 | 突破方向 |
|---------|---------|------|---------|
| ≤ 7.0 | **基础缺陷** | Token/对比度/对齐等基础问题未解决 | 继续常规优化 |
| 7.0-8.5 | **系统性不足** | 整体框架正确但各维度有明确短板 | 定向修补最低分维度 |
| 8.5-9.2 | **精细化空间** | 基础已牢固，需要微调精修 | 减法优化 + 一致性打磨 |
| 9.2-9.5 | **维度天花板** | 当前优化维度已耗尽（阈值全达标） | **策略转向：换维度思考** |
| ≥ 9.5 | **媒介限制** | HTML/CSS 原型能力上限 | React 实现阶段才能突破 |

**关键规则**：当任何维度进入「维度天花板」(9.2-9.5) 时，AD 必须在评分卡中明确指出：
1. 该维度已用尽哪些优化手段
2. 建议转向哪个新维度
3. 业界参考（哪个产品通过什么手法在这个维度上做到了更高分）

### 否决权规则

- 可**降级**某项 polish 变更（如把 `bolder` 降为 `normalize`）
- 可**移除**过度的 `delight`/`overdrive` 效果
- **不可否决**：功能性修复（P0）和可访问性修复

### 使用工具

- Chrome DevTools MCP: `evaluate_script` 批量提取 computed styles → 统计高亮/描边/色彩面积
- Chrome MCP: `take_screenshot` 对比上一版本截图 + 跨页截图
- impeccable skills: `critique`（审美评价）、`quieter`（降级过度装饰）
- WebSearch: 查找标杆产品（Bloomberg Terminal / Linear / Vercel / Raycast）截图做气质参考
